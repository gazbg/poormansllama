## 2026-10-01 (host-only): the activation slab's second half IS resident, telemetry reports the sum exactly, and the under-reporting suspicion is WITHDRAWN

**The question.** `init()` allocates the layer-major activation slab as `2 * slab_half_bytes`, while `byte_account`, `graph_footprint` and `run_start` all report `slab_half_bytes`. That looked like a 2x under-report worth 390.6 MiB — the same order as the entire unaccounted term — and the owner asked it be settled.

**Settled, host-only, no GPU run.** From the trace's own `act_bind` events: **both `slab:0` and `slab:1` are bound**, 49/49 chunks each at ubatch 1024 and 98/98 at ubatch 512, each reaching `max_end = 204,800,000 B = 195.3 MiB`. **Resident total 409,600,000 B = 390.6 MiB. Reported 409,600,000 B. `RATIO resident/reported = 1.000`.** Analyzer `build/stock-levers/act-slab-residency.py`.

**The suspicion was MY error, and the cause is worth keeping.** Each half is 195.3 MiB, not 390.6, because **`n_embd_io` is `hparams.n_embd_inp()` (`llama-layer-streaming.cpp:3131`) = 2048, not the 4096 model hidden size.** I had assumed 4096, which made the half's extent come out 2x too large and manufactured an apparent under-report the data never contained. **The telemetry is correct and was correct all along.** The two halves are A/B double-buffering, which is what lets one chunk's activations be written while the previous chunk's are still being consumed — the pipelining that depth-2 slot windows extend to the activation side.

**The act-slab law is now mechanistically derived, not just empirical:**
`act_slab = 2 x n_embd_inp(2048) x pp_tokens x dtype_bytes` = **8,192 B/token bf16, 16,384 B/token f32**. This reproduces **all 16 recorded datapoints exactly**, including the two that had looked anomalous: pp 262,144 f32 -> 4,294,967,296 B (= 2^32) and pp 200,000 bf16 -> 1,638,400,000 B. The law previously recorded in `AGENTS.md` and reconciliation §10.2 is unchanged and correct.

**Effect on the 8 GB arithmetic: none.** The slab at a full 262,144-token prompt is 2,048.0 MiB, 2 slots need 8,775.3 MiB, 1 slot 8,277.7 against 8,192 — unchanged. **Effect on T-GPLR-68: one candidate eliminated.** The unaccounted term is still unaccounted; a first accounting suspect turned out not to be a finding, which is now recorded in the task as the standing caution (check the source's own unit before believing an accounting discrepancy).

**Evidence.** `build/stock-levers/act-slab-residency.py`; traces `ab18-tg38x`, `ab16-f1024`, `ab16-f512` (`act_bind`, `graph_footprint`, `byte_account` records); source `third_party/llama.cpp/src/llama-layer-streaming.cpp:3131` and the `init()` allocation. ## 2026-10-01 (ab18b, host-only): the per-layer token-generation decomposition — and a RETRACTION of the "788 us/layer of overhead" hypothesis

**What the per-layer profile actually shows: a 1:4 periodic structure, and it is the model, not the placement.** Layers **3, 7, 11, 15, 19, 23, 27, 31, 35, 39** cost **~2,075 us** each; every other layer costs **~640-700 us**. ## 2026-10-01 (ab16): T-GPLR-66 CLOSED — the `alloc_spill` crash is fixed, the depth-2 ubatch curve is complete, and **ubatch 1024 is the fastest configuration that actually fits 8 GB**

**The defect.** `alloc_spill` (`src/llama-layer-streaming.cpp`) sized its spill buffer as a **flat sum** of the pending tensors' alloc sizes rounded up once to 32 B, while `alloc_tensors` **realigns every tensor as it walks**. A pending set with odd-sized tensors therefore needs per-tensor padding the sum omits, and because the overflow always lands on the **last** tensor, only the generic `finish_build: input buffer exhausted and spill allocation failed` ever surfaced. Proof from ab15's own log: `tensor 'leaf_3' exceeds backing buffer (offset=802848 size=4 buffer=802848 align=32)` — `buffer=802848` IS the spill buffer, allocated at exactly the cursor the walk had reached, for a 4-byte tensor. **Fix:** size the spill by walking it the way `alloc_tensors` will, via `ggml_backend_buft_get_alignment`. The three silent-false paths now each set a distinguishing `error_msg`.

**A misreading worth recording.** The `exceeds backing buffer` line was initially read as evidence AGAINST this cause. It is not: it also appears 5x in **working** arms, because overflowing the *primary* input buffer is normal and is what the spill exists for. Separately, these run logs are UTF-16 **with BOM** — `iconv -f UTF-16LE` mis-parses them and silently finds nothing; `tr -d '\000'` is the correct reader. A falsification was nearly accepted on a broken pipe.

**Validation.** Host first: `test-layer-streaming-layout` and `test-layer-streaming-tg-spec` both PASS. Then **ab16**, one mutex hold, 5 arms, `gpu_pre`/`gpu_post` clean, mutex released, **VERDICT PASS**. ubatch **1024 and 2048 completed at exit 0** where ab15 aborted with 0xC0000409 on the identical configuration. **Glossary.** *PP* is prefill / prompt processing; *TG* is token generation. *LM* is the layer-major prefill engine with expert-bank residency; *stock* is the unmodified anchor `llama-server`. *ISO-VRAM* means the two sides were compared at equal measured device-memory peak, not equal nominal settings. *Handoff* is the PP->TG migration that makes sustained generation possible. *Fit target* is stock's `--fit-target`, the free-VRAM margin the fitter must leave per device. *Residency* is how many of the 42 decoder layers are device-resident. *Route union* is the fraction of a layer's routed experts that some token in the batch selects. *WDDM* is the Windows display driver's memory accounting, polled per process. *UBatch* is the chunk size prefill is processed in.
