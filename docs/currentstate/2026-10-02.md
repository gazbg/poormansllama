## 2026-10-02 (3 GPU holds, host suite): `--kv-graph-pad 256` token generation is FIXED in the row-set executor. The guard tested a different question from the one the executor asks. Measured: shapes now match (768==768, 50176==50176), exactly 1 rebuild, and TG +28% at the 512 shape. ONE THING IS UNRESOLVED: the pad and no-pad arms agree for 42 tokens and then diverge

**Task.** Owner: "Fix the `--kv-graph-pad 256` token generation failure in the
row-set executor so shape-matched comparisons become possible again." The
failure was reproducible and previously unfixed: `layer_streaming_compute` died
on "graph set (mode 1, n_tokens 1, rs_z -1, n_outputs 1) does not match current
ubatch shapes" at **TG decode step 0** (`tg73-d1-pad`, exit 1).

**Root cause -- the predicate answered a different question than the executor.**
T-GPLR-71's `should_arm_view_rebuild` delegated to `view_covers_live`, whose
rule was `built >= required`: "is the built attention view WIDE ENOUGH to be
safe?". The executor does not ask that. Reuse is admitted only by
`can_reuse_kq_mask()` in [llama-graph.cpp:51](third_party/llama.cpp/src/llama-graph.cpp#L51),
whose rule is `kq_mask->ne[0] == mctx->get_n_kv()` -- **exact equality**, because
a graph's kq_mask is baked at its build width. And the phase-1 (TG) set is
prebuilt BEFORE the pad is armed: `--kv-graph-pad` is applied at the
prefill->generation boundary via `ctx->set_attn_view_pad()`
([main.cpp:5797](third_party/llama.cpp/tools/layer-streaming/main.cpp#L5797)),
so the set carries `built = n_pad = n_ctx = 262,144` while the first generated
token needs `GGML_PAD(50001, 256) = 50,176`. `262144 >= 50176` passed, nothing
rebuilt, and the executor died one step later. Wider is not safer here; it is
unusable. The whole-cache pin was the only configuration that had ever worked,
so the two rules could not disagree before.

**Fix 1 -- engine.** `view_covers_live` -> `view_matches_live`, exact equality
([llama-layer-streaming.h](third_party/llama.cpp/src/llama-layer-streaming.h)).
The fail-safe ordering (unknown width -> rebuild, no attention cache -> reuse)
is unchanged. **LEGACY EQUIVALENCE IS NOW A TESTED PROPERTY, not a hope**: the
host test enumerates `==` and `>=` over {-1, 0, 256, 50176, 262144} and requires
them to agree, which is exactly why `--kv-graph-pad 0` stays bit-for-bit
unchanged (with the pad unarmed both sides are the same constant).

**Fix 2 -- checker.** `ls_phase_build_allowance` gains `view_pad_rebuild_seen`,
set by the `tg_view_rebuild` event the guard emits. Deliberately NOT cleared by
`end_phase()`: unlike handoff and the S2 narrowing, a pad rebuild can land on
any generation token (measured: token 1, then token 177 at pad 256), so a
phase-boundary reset would silently un-account a mid-phase rebuild.

**Fix 3 -- checker plumbing, and the reason fix 2 alone did nothing.**
`note_event()` was called only from the `handoff` and `rowset_narrow` branches
of the dispatch chain, so the struct's own comment -- "the single event -> state
mapping, so a new topology-change event cannot be honoured at one call site and
forgotten at the other" -- was false for any event without a branch of its own.
`tg_view_rebuild` was silently dropped, so the first re-run of the fixed engine
still exited 1 on "phase_summary.graph_builds != 0". Measured directly: the
engine had already succeeded (`run_end exit_status 0, failed false, 128
tokens`, `kv_view_built 50176 == kv_view_live 50176`) while the checker rejected
the trace. `note_event` is now called for every event in both checkers. It does
NOT weaken the rule: the allowance is driven by the guard's own decision event,
so a build with no matching `tg_view_rebuild` is still a violation.

## 2026-10-02 (1 GPU hold + host analysis, owner-directed): attention in the K-cache TG path is ALREADY 100% on the GPU. The 75% "never device-only" is 10-of-40 layers carrying 75.9% of attention compute; the other 30 are gated-delta-net, and their ONLY host nodes are 60 views of a 4-byte i32 graph INPUT. There is no attention compute to move. The real headroom is the 57.5% of wall spent on row-set transfer

**Task.** Owner: "Work out how to get attention onto the GPU in the K-cache
token generation path, since it is 82.3% of compute and currently never runs
device-only." Both halves of that premise were tested against the K=2 TG trace
(`build/llama-cuda/logs/tg73-k2/tg74-partdev.jsonl`, 128 tokens) and one new
1 Hz-free 14 s arm.

**The 82.3% is right; "never runs device-only" is wrong, and it is wrong
PER LAYER, not slightly.** Attention is 82.62% of the compute bucket
(2,592,611 / 3,137,953 us). `attn_dev` is **1 (device-only) on 1,280 of 5,120
layer events and 2 (mixed) on 3,840** -- and it is not a time split. Every one
of the 128 TG ubatches contains both values. The split is exactly by layer
index: **il = 3, 7, 11, 15, 19, 23, 27, 31, 35, 39 are device-only on all 128
tokens; the other 30 are mixed.** 1,280 / 40 = 32 and 3,840 / 40 = 96 are the
same 10 / 30 split, confirmed by hand-rolled logic in
`is_recr_impl[i] = ((i + 1) % full_attn_interval != 0)` with
`full_attn_interval = 4` ([qwen35moe.cpp:42](third_party/llama.cpp/src/models/qwen35moe.cpp#L42)):
il % 4 == 3 is **full attention**, the other 30 are **linear attention (gated
delta net)**. The layers that are already device-only carry **75.9% of
attention compute** (15.36 of 20.25 ms/token); the layers labelled "mixed"
carry the remaining **24.1%** (4.89 ms/token).

**T-GPLR-79 (shipped + hardware-exercised): the 60 host nodes are named.**
`ls_ops_census()` gained `rowset_host_names_a/b`. First attempt returned
`{"(view)": 60}` and was useless: ggml names a view `"%s (view)"` from its
source ([ggml.c:3725](third_party/llama.cpp/ggml/src/ggml.c#L3725)), so a view
of an unnamed source prints as bare `(view)`. The census now walks `view_src`
to the memory root and keys on root op + shape + type + hop count. Result,
exactly 60 host nodes, two distinct roots:

```
   30  NONE ne=[1,1,1,1] type=i32 hops=1 rootbuf=host rname='leaf_3'
   30  NONE ne=[1,1,1,1] type=i32 hops=1 rootbuf=host rname='leaf_3'
```

`leaf_3` is ggml's own auto-name for an unnamed tensor added to the graph as a
LEAF rather than through srcs: `ggml_format_name(node, "leaf_%d", n_leafs)`
([ggml.c:7168](third_party/llama.cpp/ggml/src/ggml.c#L7168)). One per recurrent
layer, two views of it. It is op NONE, i32, `ne=[1,1,1,1]` -- **4 bytes** --
and INPUT-flagged, so the layer-streaming build path placed it in the host
input buffer: `buf_inputs` is deliberately allocated with
`ggml_backend_cpu_buffer_type()` ([llama-layer-streaming.cpp:3436](third_party/llama.cpp/src/llama-layer-streaming.cpp#L3436)
and `finish_build` at :3936) precisely so "the scheduler copies them H2D per
split, exactly like the normal path", with `alloc_spill` as the host fallback
when that buffer is exhausted (:1198).

**Therefore the mixed classification carries no compute.** A VIEW is in
`ls_op_is_metadata_only` because it is an explicit `// nop` in
`ggml_compute_forward`; it moves no bytes and computes nothing, and here the
thing it views is a 4-byte input scalar in the host input buffer, by design.
The new census shows **every real op in part A on the device**:
`FLASH_ATTN_EXT 10, GATED_DELTA_NET 30, SSM_CONV 30, MUL_MAT 270, CPY 200,
MUL 200, RMS_NORM 130, UNARY 130, GET_ROWS 120, SOFT_MAX 40, CONCAT 30,
TRANSPOSE 30, PERMUTE 30, ROPE 20, ...` and `part_b_host = {}`. With
T-GPLR-78's filter applied, all 40 layers now classify device-only. The
recurrent state is not implicated: the run log shows
`llama_memory_recurrent, layer N: dev = CUDA0` for all 30 and
`CUDA0 RS buffer size = 62.81 MiB`.

**The reframing that decides the work: 82.62% of compute is 27.2% of wall.**
TG wall is 74.50 ms/token at 291.3 MB/token moved. Transfer is **42.83 ms/token
= 57.5% of wall**, wait 8.20 ms = 11.0%, compute 24.52 ms = **32.9%**
(buckets overlap, hence 101.4%). Attention compute is 20.25 ms/token =
**27.2% of wall**; the part of it that is NOT device-only is 4.89 ms/token =
**6.6% of wall**, and the measurement above says that 6.6% has no host compute
in it to recover. The genuine TG bottleneck is the row-set expert transfer,
which at 42.83 ms/token is **1.75x larger than all compute combined**.

**Unknown, stated rather than papered over.** The exact provenance of the
4-byte i32 leaf is not identified beyond "one unnamed INPUT-flagged scalar per
recurrent layer". It is immaterial to the placement conclusion -- it is an
input scalar of no data -- but it is NOT identified.

**Recommendation.** Do not spend work moving attention to the GPU: it is
already there, and the ceiling on that whole line of attack is 6.6% of TG wall
with a measured cost of zero. Redirect to the 57.5% row-set transfer.

**Validation.** Full `cmake --build build/llama-cuda --config Release`, no
`--target`. `tools/run-tests.ps1 -Suite host` 77/77 on the T-GPLR-78 build;
T-GPLR-79's telemetry change is a census-only addition over the same host
build. One GPU hold, 14 s, exit 0, wrapper verdict PASS,

## 2026-10-02 (1 GPU hold, 2 arms, owner-directed "maybe do not use mmap?"): the answer is NO -- `--no-mmap` ADDS ~the whole model file (19.92 GiB) to host commit. It is not a RAM lever. But it made PP FASTER in both matched pairs, and that lead is unexplained

**Task.** Owner question, mid-session: "maybe do not use mmap?" -- i.e. is the
file mapping what pins host RAM, and would `--no-mmap` relieve it? Two arms at
ctx 262,144, K=2, `--residency moe-expert-bank --pp-schedule batch-major
--residency-tg --layer-slots 2 --kv-cache q8 --copy-source direct`, batch-major,
no handoff, differing from the mmap arms ONLY by `--no-mmap`. The 1 Hz
committer (`tools/ram-commit-poller.ps1`, `build/llama-cuda/logs/ram/
ram-bisect.csv`, 1,707 samples 20:38:36..21:12:46 UTC) was live across both
windows; the earlier 50k mmap baseline sits in the 6 s-cadence predecessor
`ram-live.csv` (390 samples, 19:57:41..20:37:16 UTC). Both arms exit 0, wrapper
verdict PASS, `gpu_pre=clean gpu_post=clean`.

**Host facts used.** Model file 21,388,319,008 B = 19.92 GiB. Physical RAM
66,234,945,536 B = 61.68 GiB. Commit limit 103.70 GiB. Machine idle floor,
measured across three separate idle windows: 12.82-13.92 GiB committed.

**MEASURED -- committed-memory step, idle floor to in-run peak.**

| arm | PP / TG tokens | idle | peak | STEP | min available |
|---|---|---|---|---|---|
| c3-ctx262144 (mmap) | 512 / 4 | 13.37 | 24.62 | **+11.25 GiB** | 34.06 |
| e1-nommap-512 | 512 / 4 | 13.66 | 43.42 | **+29.75 GiB** | 33.21 |
| tg74-partdev (mmap) | 50,000 / 128 | ~12.4 | 71.82 | **+59.4 GiB** | 0.34 |
| e2-nommap-50k | 50,000 / 8 | 13.66 | 90.48 | **+76.82 GiB** | 0.00 |

The deltas are **+18.50 GiB** and **+17.4 GiB** -- 93% and 87% of the entire
19.92 GiB model file. The hypothesis is REFUTED, and it is refuted in the
opposite direction to the question: the file mapping is not what pins RAM.
`--no-mmap` converts 19.92 GiB of clean, reclaimable, file-backed pages into
anonymous private pages, which are charged against commit and cannot be
dropped without a pagefile round-trip. The cost of `--no-mmap` is
approximately the cost of holding the model in RAM permanently.

**MEASURED -- the staging hold itself is unchanged.** Add the file constant
back to each mmap arm: 11.25 + 18.50 = 29.75 vs 29.75 measured; 59.4 + 17.4 =
76.8 vs 76.82 measured. Both land within 0.1%. The transient hold that this
session's bisect tied to staged bytes (r = 0.998) is untouched by the mapping
mode; `--no-mmap` only adds a constant on top of it.

**MEASURED -- PP got FASTER, and this is not explained.**
Pair A (512 tok, run_start byte-identical except volatile fields, 24 fields
equal): 64.742 -> 240.738 tok/s, **+272%**, on the identical
18,327,011,328 B moved with the identical 38 evictions. Effective staging
bandwidth 2.32 -> 8.62 GB/s. Pair B (50k): 247.504 -> 348.659 tok/s, **+41%**,
on the identical 898,023,555,072 B moved with the identical 1,958 evictions;
transfer time 193.06 s -> 150.97 s, i.e. 4.65 -> 5.95 GB/s. Both arms report a
`byte_account` that differs only in `run_id`, so the VRAM plan is byte-identical.
Mechanism: **unproven.** The staging byte counts are identical, so this is a
per-byte cost difference in the copy path, not less traffic.

**MEASURED -- TG is split by workload, and the 50k TG number is confounded.**
Pair A TG (4 vs 4 tokens, rate-comparable): 8.411 -> 13.002 tok/s, **+55%**,
i.e. TG also got faster. Pair B TG (8 vs 128 tokens, NOT rate-comparable):
13.422 -> 3.850 tok/s. Normalising per token, 259.7 ms vs 74.5 ms, of which
compute is 154.5 ms vs 24.5 ms -- a 6.3x compute inflation at 1.06x the bytes
moved (308.5 vs 291.3 MB/token), while transfer per token is flat (39.0 vs
42.8 ms/token). The 8-vs-128 token count is a real confound and this number
should not be quoted as a `--no-mmap` TG regression on its own. What survives
the confound: with 17.4 GiB more anonymous memory resident on a 61.68 GiB
machine, the 50k no-mmap run drove available memory to **0.00 GiB** and
inflated the per-token compute bucket 6.3x at constant transfer. Pagefile
round-trips of the weight buffers is the EXPECTED mechanism; it is not measured.

**CONFOUNDS on the PP lead (do not treat the speedup as established).** One
sample per arm. Both matched pairs straddle the T-GPLR-76 rebuild (c3 and
tg74-partdev ran the T-GPLR-75 binary; e1 and e2 ran T-GPLR-76). T-GPLR-75 and
-76 are telemetry-only -- one `graph_backend_ops` census per run and two extra
integer fields per `tel_layer_compute` -- so they are expected to be
performance-neutral, but that is expected, not measured. A clean A/B needs both
arms on ONE binary; because `--no-mmap` is a runtime loader flag and not a tree
change, that A/B needs no rebuild and therefore no side-copy of the exe/DLLs.

**Answer to the owner.** Do not adopt `--no-mmap` as a memory fix -- it is the
single largest RAM regression measured in this session (+17 to +18.5 GiB, ~90%
of the model). Keep the mapping. The PP lead is real in sign across two
workloads and worth one controlled repeat, because PP is charter priority #1
and +41% at the 50k shape would matter -- but it is a throughput question,
not a capacity one, and it must be re-measured single-binary before it is
believed. Evidence: `build/llama-cuda/logs/tg78-nommap/{e1,e2}*.jsonl`,
`build/llama-cuda/logs/tg73-k2/tg74-partdev.jsonl`,
`build/llama-cuda/logs/tg75b-commit/c3-ctx262144.jsonl`,
`build/llama-cuda/logs/ram/ram-bisect.csv`, `ram-live.csv`.

non-zero exit instead of truncating 16 entries. This closes the specific
destruction path; it does not make the tool safe against an operator who
deletes the manifest, and the backup step must stay in the procedure.

**Standing rule for this repo, from this incident.** Any tool that rewrites a
tracked documentation file must have its output diffed by heading COUNT, not
by exit code, before the rewrite is believed. A PASS verdict is not evidence
that content survived.

### 2. Why this OVERTURNS the earlier reading

`GGML_OP_VIEW` **allocates nothing and executes no kernel** — it is a
zero-copy alias of existing memory, so a host buffer on a VIEW costs no compute
and no time. They most likely alias the host input tensors bound through
`alloc_tensors(buf_inputs.get(), ggml_backend_cpu_buffer_type(), ...)`
(`src/llama-layer-streaming.cpp:3936`).

So `ls_classify_graph_backend` was counting a metadata node as evidence of
host-side execution. **A graph with 2,360 device nodes and 60 zero-op views was
labelled `2 = MIXED`, and my T-GPLR-75 entry reported "75% of attention is
MIXED", which reads as "75% of attention runs on the CPU". That is wrong.**
The corrected statement is: **essentially 100% of attention's compute is on the
GPU in the K-cache TG path**, which *strengthens* the T-GPLR-75 conclusion that
`--residency-tg` is a GPU-side path.

**Not yet fixed:** `ls_classify_graph_backend` still counts metadata ops, so
`attn_dev = 2` remains a misleading field. It should exclude no-kernel ops
(`VIEW`, `RESHAPE`, `TRANSPOSE`, `PERMUTE`, `CONT`) or report a separate
kernel-bearing classification. Until then, read `attn_dev = 2` as "contains at
least one host-backed VIEW", not "runs partly on the CPU".

### 8. Tooling gotcha recorded the hard way

The agent file tools (`write_file`, `glob`, `str_replace`) resolve to the
Freebuff worktree `.freebuff/worktrees/<id>/`, **not** to
`C:\Development\AI\qwen38GZI`, and cannot see `third_party/` at all. A
`write_file` reporting success can therefore land a file in a tree that is not

### Part 2 — the act slab CANNOT be sized per chunk; the earlier suggestion was wrong

I offered the owner "size the act slab per chunk, not per prompt" and then
checked it before coding. **It is not available, for a structural reason.**

**The slab is full-prompt by construction, not by over-provisioning.**

1. `src/llama-layer-streaming.h:419-423` describes *"two stable **full-prompt**
   F32 slabs A and B. One 1-D slab tensor owns both halves; every PP chunk gets
   a non-aliasing `ggml_view_2d` slice of each slab, bound at graph build time
   (per-chunk graph sets)."* `pp_tokens` is documented at :433 as the
   *"full-prompt token count (slab width)"*.
2. `llama_ls_slab_region_of` (`src/llama-layer-streaming.cpp:205`) computes
   `half = Σ_c n_tokens_c × n_embd_io × elt` — the sum over **all** chunks, i.e.
   the whole prompt. There is no per-chunk term anywhere in it.
3. `begin_set` sets `slab_off_A = region.offset; slab_off_B = region.offset;`
   (:3714 area) — the **same offset in both halves**. So A and B are the two
   sides of one activation pair, not chunk double-buffering, and the 2× factor
   in the runner's formula is load-bearing rather than slack.
4. **The reason it must be full-prompt is the definition of the schedule.**
   Layer-major PP runs layer L across chunks 0…N, then layer L+1 across chunks
   0…N. Layer L+1's chunk 0 consumes layer L's output for chunk 0, so every
   chunk's activations must survive an entire layer sweep. Per-chunk sizing
   would break the schedule, not shrink it.

Sizing formula, `tools/layer-streaming/main.cpp:4593`:
`act_slab_bytes = n_embd_inp × pp_tokens × 2 × slab_elt`. At n_embd 2048 /
bf16 this reproduces ab20's `act_slab_bytes: 409600000` exactly at
pp_tokens 50,000, and gives 2,147,483,648 B = 2,048 MiB at 262,144.

## 2026-10-02 (host-only, NO GPU): per-layer K is CORRECT and maximally valuable at small K (+1.96 pp at K=1) — but K=2 does not fit at 8 GB/262k at all, and the row cache's real currency is PROMPT LENGTH: a K=1 cache costs 69% of the maximum prompt

**Question from the owner.** Per-layer K "is what the code should do anyway".
But K=2 may be the ceiling: 262k context must fit under 8 GB VRAM, so is K=2
acceptable, or can we take a bit more? Host-only, no GPU. Tool `%TEMP%kfe.py`;
evidence the ab20 footprint and the recorded routing trace.

**1. The proposal's premise is right, and the usual intuition is INVERTED.**
Per-layer K's advantage over flat K **shrinks as K grows**, so it is worth most
exactly where the budget forces you:

| budget | flat hit | optimal per-layer | gain | staged MiB/token |
|---|---|---|---|---|
| **K=1** (540 MiB) | 17.55% | **19.51%** | **+1.96 pp** | 445.2 -> 434.7 |
| **K=2** (1,080 MiB) | 34.71% | 35.50% | +0.78 pp | 352.5 -> 348.3 |
| K=3 | 45.04% | 45.45% | +0.41 pp | 296.8 -> 294.6 |
| K=4 | 52.10% | 52.74% | +0.64 pp | 258.7 -> 255.2 |
| K=8 (4,320 MiB) | 72.17% | 72.41% | +0.24 pp | 150.3 -> 149.0 |

So the owner is right that per-layer beats global at identical VRAM. It is worth
**+1.96 pp** at the only K that fits — and the byte effect of that gain is
**2.4%** (445.2 -> 434.7 MiB/token).

**2. K=2 does not fit. Only K=1 is free.** Measured baseline 8,160,768,000 B =
7,783 MiB; an 8 GiB card is 8,192 MiB, so slack is **409.3 MiB**.

| lever | MiB freed | slack |
|---|---|---|
| `--reserve-mib 0` (pure preflight headroom, no functional cost) | 512.0 | **921.3** |
| also `pp_tokens` 50k -> 30k (act slab 390.6 -> 234.4) | 156.2 | 1,077.5 |
| also `pp_tokens` -> 25k | 195.3 | 1,116.6 |
| also `--layer-slots 2 -> 1` (costs PP staging overlap) | 498.0 | 1,419.3 |

- **K=1 = 540 MiB: FITS at `--reserve-mib 0` alone, +381 MiB spare.**
- **K=2 = 1,080 MiB: does NOT fit.** Short by 158.7 MiB at reserve 0, and still
  **short by 2 MiB even at pp_tokens 30k** — it needs <=25k, or one slot.
- **K>=3 = 1,620 MiB: unreachable at every lever, including 1 slot.**

**3. The decisive reframing: the row cache's currency is PROMPT LENGTH.**
`act_slab_bytes = n_embd_inp * pp_tokens * 2 * slab_elt`
([main.cpp:4581](third_party/llama.cpp/tools/layer-streaming/main.cpp#L4581);
solved `n_embd_inp` = 2,048 from the recorded 409,600,000 B at 50,000 tokens,
bf16). **The activation slab is sized for the WHOLE prompt, not the chunk.**
Baseline without the slab is 7,392 MiB, so:

| pp_tokens | act slab | total | 8 GiB? |
|---|---|---|---|
| 50,000 | 391 MiB | 7,783 MiB | fits |
| **102,388** | 799 MiB | **8,192 MiB** | **the ceiling, reserve 0, no cache** |
| 150,000 | 1,172 MiB | 8,564 MiB | over by 372 MiB |
| 262,144 | **2,048 MiB** | **9,440 MiB** | **over by 1,248 MiB** |

**A K=1 row cache cuts the maximum prompt from 102,388 to 33,268 tokens (-69%).**
A K=2 cache makes it **negative — it cannot coexist with any prompt at all.**

**4. A distinction the charter's "262,144 tokens" hides.** `ctx_size` 262,144 is
the **KV cache capacity** (q8 KV = 2,720 MiB) and that fits fine; `pp_tokens` is
the **actual prompt**, which sizes the act slab and is the binding term. A
262,144-token *prompt* does not fit on 8 GiB with this design, at any K.

**5. "8 GB" must mean 8 GiB for any of this to run.** At ctx 262,144 the
measured footprint is 7,783 MiB against 7,629 MiB for an 8 GB **decimal** card —
**over by 153.3 MiB**. Every figure above assumes 8,589,934,592 B.

**Recommendation.** The owner's per-layer instinct is analytically sound and the
measurement supports it, but **K is not the lever**. K is bounded by a negative
VRAM budget, and spending what little room exists on a cache costs 69% of the
maximum prompt length to buy a 2.4% byte reduction on a path already measured
16x slower in transfer time. **The lever is the activation slab**: decoupling it
from total prompt length is worth more VRAM than any K choice (390.6 MiB at 50k,
2,048 MiB at 262k), it is pure prefill scope, and it is what actually decides
whether a long prompt fits on the target card. Per-layer K stays a correct,
low-value refinement to revisit only if the slab is fixed and VRAM is free.

## 2026-10-02 (host-only, NO GPU): the owner's simpler rule ("in-flight wait, queued don't") is ALREADY implemented in the row-set path — and the real PP loss is a flag-off registration stall of~1.8-2.0 s, which also CORRECTS the disk-paging attribution above

**Trigger.** A proposed task said "replace the boolean wait-or-don't with a
deadline: `eta(layer)`, and wait iff `eta < host_cost(layer)`", claiming the
predicting instrument "already half-exists" in the lookahead distance and the
recency stamp. The owner replied that the model can be simpler: **if the expert
is already picked up for transfer, wait; if it is still in the queue, probably
not; and there is no way to cancel in-flight data.** Host-only, no GPU.

**1. The owner's rule is already the implemented contract — in the row-set path.**
`llama_ls_spec_cancel_policy(n_free, reserve, n_want, n_pending)` returns
`need = pending fills to cancel, oldest-first`, and only touches **PENDING**
work ([llama-layer-streaming.h:2203](third_party/llama.cpp/src/llama-layer-streaming.h#L2203));
the state contract says a position whose bytes are **in flight**, or whose
cancellation has not completed, is not reusable ([:300](third_party/llama.cpp/src/llama-layer-streaming.h#L300)).
That is precisely "in-flight -> wait, queued -> don't", with per-row states and
a host test over the same function the engine calls. So the semantics are not
missing; they are in `--residency-tg`, the path the K-cache analysis concluded
is **not worth a hardware arm**. Nothing new to design.

**2. For staging copies there is no cancel path, and there should not be one.**
There is no cancel/abort for H2D staging (the only `cancel` in the file is the
row-set one). The data says none is needed: PP `ready_latency_us` has
**p50 = 335,658 us, mean 408,243, max 723,369** against a PP pass wall of
18,153,244/49 = **370,474 us per ubatch**. So a staged copy is issued roughly a
**whole ubatch (~336 ms) before it is consumed**. `host_submit_us`, the real host
enqueue cost, is p50 **42 us**, max 141. With that much runway the eta term is
already slack and "wait or don't" is not a decision the PP path is losing time
on. (TG `ready_latency_us` p50 = 3 us, max 9,745 — that is the no-copy handoff
path, and TG stages nothing at all, per the previous entry.)

**3. The eta instrument does NOT already half-exist.** `ready_latency_us` is
**not** a DMA landing time: it is submit -> consumer-observation, gated by the
slot protocol, which is exactly why its p50 equals one ubatch period in PP.
And ggml has **no non-blocking event query** — `event_query` / `cudaEventQuery`
appear nowhere in `ggml/include/` or `ggml/src/`; only record / wait /
**synchronize** (blocking). `ev_copy_ready` does exist per slot, so a true
landed-time probe is *possible*, but it needs a small new CUDA-backend accessor
first. Cheap, but not free and not present.

**4. CORRECTION to the cold-start entry above: the cause is the deferred
`cudaHostRegister` commit, NOT disk paging.** The tree already diagnosed it at
[llama-layer-streaming.h:297](third_party/llama.cpp/src/llama-layer-streaming.h#L297):
"`register_all_pkg_sources` issues every `cudaHostRegister` up front, and the
**DEFERRED work of those calls commits on the first submission**, so the first
staging copy of the sweep **stalls for it (measured 1814.3 ms at 4k; the calls
themselves are ~1.6-2.3 ms)**." My independently measured first-pass penalty is
**1,939,304 us (ab19) / 2,006,941 us (ab20)** — the same magnitude, and the
same **pass-1-only** signature, because the deferred commit can only hit the
first staging copy. The owner's "this does not guarantee the data is in memory"
instinct was pointing at the right neighbourhood of the system; the specific
mechanism is the registration commit, not the disk. **The disk-paging reading in
the previous entry is WITHDRAWN as unproven** — disk I/O versus Windows
file-cache behaviour was never separable in that comparison.

**5. The fix already exists and is DEFAULT OFF.** `--pp-span-pace 1`
(T-GPLR-56 A3, owner-ratified 2026-09-22, `pp_span_pace = 0` = off default at
[main.cpp:3184](third_party/llama.cpp/tools/layer-streaming/main.cpp#L3184))
issues the same total registration commit in group order a bounded distance
ahead of the copy that needs it, keeping pending unlocked bytes near one group
instead of 17.23 GiB. It is **additive by construction** (`pp_span_pace == 0`
never enters the state and `register_all_pkg_sources()` is untouched), and
`--pp-span-pace 1` **does not appear in the ab19 or ab20 command lines** — the
+26.5% winner ran with it off. It has never been A/B'd on this hardware.

**Recommendation.** Do not build the eta scheduler: the rule is already

decision is not binding, and a real eta probe needs a ggml backend addition

staging gap**, and prefill is the charter's priority 1. Score it on **pass-1 wall
specifically**; scoring on a warm model reproduces how it has stayed hidden.
Keep `--pp-span-pace 0` as the control arm in the same hold.

## 2026-10-02 (host-only, NO GPU): the proposed byte-accurate PCIe ledger is WITHDRAWN as unnecessary — byte accounting already exists, is free, and is exact; and the owner's mmap disk-paging worry is REAL, already measured, and costs 10.7-11.1% of the first PP pass

**Trigger.** A proposed task said "build a byte-accurate PCIe traffic ledger
before designing any policy (high impact, low effort)". The owner pushed back:
something on another branch counted bytes and **slowed the transfer a lot**;
the default `mmap` source might fault from disk; pinning host memory might be
better. Host-only, no GPU, no engine change. Tools `%TEMP%cold.py`; evidence
`ab19-ctl38x-a1-u1024.jsonl` and `ab20-g71x-a1-u1024.jsonl`.

**1. The ledger is unnecessary — it already exists, is free, and is exact.**
`nbytes` is computed at the copy site anyway and summed into
`total_bytes_transferred` ([llama-layer-streaming.cpp:2231](third_party/llama.cpp/src/llama-layer-streaming.cpp#L2231),
[:4146](third_party/llama.cpp/src/llama-layer-streaming.cpp#L4146)). Counting is
one `size_t` add: no sync, no compare, no extra copy. Measured, ab20:
**PP `bytes_transferred` = 18,327,011,328 B**, identical across passes. So the
"no byte accounting on the mmap path" claim in earlier entries is **WITHDRAWN —
it was wrong.**

**2. Where the zeros really come from.** `copy_submit` emits `bytes: 0` at
[:3983](third_party/llama.cpp/src/llama-layer-streaming.cpp#L3983),
[:4011](third_party/llama.cpp/src/llama-layer-streaming.cpp#L4011) and
[:4030](third_party/llama.cpp/src/llama-layer-streaming.cpp#L4030) — but those
are the **handoff no-copy** paths, where a layer is already resident and **no
H2D copy occurs**. The zero is correct and meaningful. Consequence, measured on
ab20: **during TG every one of the 5,120 `copy_submit` events is 0 B and
`phase_summary` TG `bytes_transferred` is 0.** **Token generation moves ZERO
bytes over PCIe by construction** — 2 layers are device-resident, 38 execute
from host tensors, nothing is staged. There is no TG traffic to account for, so
a TG byte ledger has nothing to do.

**3. The slowdown the owner remembers was page-locking, not counting.**
The header records it exactly ([:284](third_party/llama.cpp/src/llama-layer-streaming.h#L284)):
the original mmap staging **registered and unregistered each 436 MiB file
region per bank** -- "80 registrations / 34.46 GiB of churn per run", inflating
per-launch host windows (setup 11 -> 136-228 ms) for a **net warm regression of
15-24% at 4k**. That is `cudaHostRegister` churn, not a byte counter, and it
was fixed by registering every layer's span ONCE before the timed PP. The churn
variant is still reproducible behind `--copy-source mmap-registered-churn`.

**4. The mmap disk-paging worry is CORRECT, and it is already measured — at
zero instrument cost.** PP pass 1 does byte-identical work to pass 2 (same
50,000 tokens, same 49 ubatches, same 18,327,011,328 B) yet costs more:

| | pass 1 wall | pass 2 wall | delta | in compute | in transfer | **in the staging gap** |
|---|---|---|---|---|---|---|
| ab19-ctl38x | 18,122,585 | 16,183,281 | **+1,939,304 (10.70%)** | +0.90% | +0.23% | **+91.55%** |
| ab20-g71x | 18,153,244 | 16,146,303 | **+2,006,941 (11.06%)** | +0.59% | **-0.07%** | **+94.66%** |

`gap = wall - compute` is the window where the GPU waits for the next layer's
weights: 17.4% of pass-1 wall vs 8.5-8.6% warm. Passes 2 and 3 in ab19 agree to
0.008% (16,183,281 / 16,184,576), so warm is genuinely steady-state and pass 1
is the cold one. **91.6% / 94.7% of the penalty lands in the staging gap, ~1% in
compute, ~0% in transfer.** That is the first-touch/disk-fault signature, and it
is NOT registration churn (registration happens once, before the timed PP, so it
cannot differ between pass 1 and pass 2) and NOT a transfer-engine cost
(transfer delta ~0, and `transfer_us` is submit-shaped anyway).

**5. Pinning host memory already exists.** `--copy-source pinned` allocates
per-slot pinned staging via `ggml_backend_cuda_host_buffer_type()`, and the
optional `--pp-pool` persistent pinned pool requires it. So the owner's third
point needs no new code either. The trade is RAM, not code: `mmap-registered` is
documented as "no CPU hop, pinned transfer rate, and RAM-neutral (no staging
buffers are allocated at all)", and `--pp-pool`'s `lru` policy measured a **0%
hit rate** (capacity failure) with the pool OFF in the T-GPLR-71 arms. On a box
where 38 of 40 layers execute *from the model's own mapping*, spending RAM on
staging buffers competes with the host working set.

**Not established.** How much of the ~2 s is genuine disk I/O versus Windows
file-cache behaviour is **uncontrolled** (AGENTS.md: report as uncontrolled
Windows file-cache behaviour, never as a guaranteed cold-cache condition). One
run pair cannot separate them, and pass-1 cost here happened to be cold. Also
unmeasured: whether a **decode-only** session (no PP to warm the mapping) would
fault host layers from disk during TG -- plausible given TG executes 38 layers
from those same mappings, and untested.

**Recommendation.** Drop the byte-ledger task — it costs effort and buys nothing,
because PP is already byte-exact and TG is already zero. **Promote the cold-mmap
staging gap instead**: it is ~11% of the first prefill pass, prefill is the
charter's priority 1, and the fix (`--copy-source pinned`, or a deliberate

### 1. Goal and hypothesis

**The goal** is the standing charter for this branch — maximise prompt-processing (PP) speed, then minimise VRAM, and hold PP when VRAM is crowded, at an 8 GB target card and 262,144 tokens of context. T-GPLR-71 is the token-generation (TG) leg of that.

**The hypothesis, as it stood before the fix.** During TG the decode attention scanned the **whole allocated KV cache** rather than the **live token count**, so a run holding 50,000 real tokens still paid for a 262,144-slot cache. That scan was sized at **9,000.4 microseconds per token**, about **20.8% of the TG wall**. If the attention view were sized from the live position instead, that cost would be recovered **without spending PP throughput and without spending VRAM** — the view would get *narrower*, never wider, so VRAM should be unchanged or lower.

**Why it mattered.** The charter's third clause is that PP must hold when VRAM is crowded. A TG leg that degrades with the *allocated* context is exactly the failure mode that clause exists to prevent, and it was the one place where the mechanism was paying for capacity nobody was using.

### 2. The mechanism in plain language

**Glossary (each term defined at first use, restated in full for this summary).**

- **PP (prompt processing / prefill)** — consuming the whole prompt at once, computing every token's representation in large parallel batches. Measured here in tokens per second.
- **TG (token generation / decode)** — producing the answer one token at a time. Each step is a *single* token against the entire accumulated history, which is why TG is far slower per token than PP and why it dominated the problem.
- **KV cache** — the per-token keys and values every layer keeps so later tokens can attend to earlier ones. Its size grows with context.
- **n_kv** — the number of KV positions the attention math actually walks over.
- **n_pad** — the rounding step. The engine pads a view width up to a multiple (here 256) so the GPU's kernels see a shape they like. A legacy mechanism pinned this padding; the new mechanism lets the width float.
- **view / view width** — the slice of the KV cache one graph is built to read. The whole lever of T-GPLR-71 is *choosing this number correctly*.
- **graph set** — the prebuilt CUDA execution plan, compiled for specific tensor shapes. It is expensive to build (milliseconds) and must be rebuilt if a shape changes.
- **slot** — one bounded place in VRAM where a complete layer's weights are staged while the prompt is processed.
- **layer residency** — the branch's core idea: stage one layer's weights at a time through a small fixed window of VRAM slots instead of holding the whole model on the GPU.
- **handoff** — the point where control passes from PP to TG, where session state and live weight-slot assignments are retained.
- **VRAM** — the GPU's on-board memory, the scarce resource this branch is rationing.
- **mutex hold** — an exclusive, named lock on the single shared GPU, taken for the duration of a measurement so no other project's job can corrupt it. Every timing number here was taken under one.
- **µs/token** — microseconds of wall or compute time per generated token; the unit TG speed is really made of.
- **tok/s** — tokens per second; the headline throughput number.

**In plain language.** Normally the decode step would be handed a 262,144-slot menu and told to look at all of it, even though only 50,000 slots had anything in them. The fix hands it a menu sized to what is actually on it — 50,176 slots, rounded to the 256 boundary. Same arithmetic over the tokens that exist, far less work over the empty ones. Because the menu is *narrower*, nothing has to be added to VRAM to hold it.

That created a new question, and it is the part this branch had to answer. If the view is sized to the live count and generation keeps adding tokens, the view will eventually be **too narrow** — and a too-narrow view does not crash. It silently reads a truncated history, which is a quietly wrong answer. So a **coverage rule** was added: before each generated token, check whether the built view still covers the live position. If it does, proceed. If it does not — or if the engine cannot tell — **rebuild the view and use the new one**. The fail-safe is deliberate: *unknown counts as not-covered*, because guessing wrong in the safe direction costs a rebuild and guessing wrong in the fast direction costs correctness.

### 2. The test found a REAL latent defect on its first execution of the guard

Calling `arm_tg_view_rebuild` — for the first time by anything, ever — killed the process with **exit `-1073741676` = `0xC0000094`, integer divide by zero**.

`arm_tg_view_rebuild` emits a `tg_view_rebuild` telemetry line whose last argument is `ggml_time_us()`. On Windows that is `((QPC - timer_start) * 1000000) / timer_freq`, where both statics are set by **`ggml_time_init()`**. A host test never initialises llama, so `timer_freq == 0`.

**This exact trap was already found, documented and fixed in this same file.** `llama-layer-streaming.cpp:1305-1312` carries the measured note: *"MEASURED TRAP (2026-09-22) ... dies with 0xC0000094"*, with `ggml_time_init()` added to `llama_ls_tel_mark`. The T-GPLR-71 steps 3-4 pass later reintroduced the identical hazard in a sibling function and it survived review **because that function had never been executed by anything**.

- **Was it a live production bug? No.** The runner calls `llama_backend_init()`, which initialises the timer long before the first generated token, so `timer_freq != 0` on every real path.
- **Why it still mattered.** It is a latent crash reachable by any caller that drives the module without a full llama init — and, more to the point, it means the guard's *telemetry line* could kill the process independently of its state transition.
- **Fix.** The repo's own one-liner, `ggml_time_init()`, added to `arm_tg_view_rebuild` with a comment naming the trap and pointing at the sibling fix. InitOnce-guarded, so it is free and `llama_backend_init()`'s later call is a no-op.

## 2026-10-02 (host-only): the decode attention kernel is already at ~97% of its block-wave occupancy, and the MMA specialization is UNREACHABLE at decode

**Question.** Profile the 5090's decode-attention occupancy ceiling and check whether a different flash-attention specialization could use more than 160 CTAs. **Host-only: no GPU run, no rebuild.** Re-derivation tool `build/stock-levers/fa-occupancy.py`.

**Answer: yes in principle (2-4x the CTAs) but it cannot be reached, and the kernel is not CTA-starved anyway.**

**First, a correction that invalidates a number I reported earlier.** The GPU has **82 SMs, not 170** - `TARGET_INFO_CUDA_DEVICE.numMultiprocessors` in all five `build/stock-levers/prof/*.sqlite`, stock arms included. It is the laptop GB203. My earlier "~5.9% of a 5090's thread slots" was computed against the desktop part's 170 SMs; **the correct figure is 16.3%** (20,480 threads of 82 x 1536). Occupancy arithmetic in this project must read the SM count from a profile, never from a spec sheet.

**The measured decode launch.** `flash_attn_ext_vec<256,1,Q8_0,Q8_0,0>` at **grid (1,10,16) = 160 CTAs x 128 threads, regs=255, dynsmem=0**, 228.3 us at ctx 50,176 / 557.6 us at ctx 128,000.

**The occupancy ceiling, derived not guessed.** Replaying `fattn-common.cuh`'s own `parallel_blocks` search against the observed `grid.y = 10` uniquely pins **`cudaOccupancyMaxActiveBlocksPerMultiprocessor = 2`**: with 128 threads x 255 registers = 32,640 registers per block, two blocks need 65,280 <= the 65,536-register file, and three would not fit. So `blocks_per_wave = 82 x 2 = 164`, and the search picks `parallel_blocks = 10` because 16 x 10 = **160 CTAs is the largest configuration that fits in one wave with no tail** - 1.95 of the 2 possible blocks per SM. **The kernel is register-bound, not shared-memory-bound** (`dynsmem = 0`), and **it is already at ~97% of its achievable block-wave occupancy.**

**The alternative that exists, and why it cannot be used.** An MMA specialization for our exact head size **does exist**: `fattn-mma-f16.cuh` carries `GGML_CUDA_FATTN_MMA_CONFIG_CASE(256, 256, 8, 64 nthreads, occupancy 4, nbatch_fa 64, nstages 2, Q_in_reg true)`. `ntiles_dst` is 16 for it exactly as for the vec kernel - that number depends only on the Q/K dims, not on which kernel runs. By the same launch arithmetic it would produce **grid (1,20,16) = 320 CTAs at occupancy 4**, or (1,41,16) = 656 CTAs if 8 blocks/SM fit. That is **2-4.1x the CTA count - but only flat-to-2x the threads** (20,480 or 41,984), because MMA uses **64 threads per block instead of 128**.

**And it is unreachable.** `fattn.cu`'s `ggml_cuda_get_best_fattn_kernel` hard-selects `BEST_FATTN_KERNEL_VEC` whenever KV is quantized and `Q->ne[1] <= 2` on Ada and later. Our shape is q8 KV with `Q->ne[1] = 1`, so the vec kernel is returned immediately; **the MMA branch is not merely unselected, it is structurally unreachable at decode with quantized KV.** Reaching it would need a source change to upstream's dispatch heuristic, and upstream presumably chose vec here because it measured faster.

**What this closes and what it leaves open.**
- **Closed:** "give the decode kernel more CTAs" is **not an available lever** at this shape, and the earlier occupancy worry was mis-scaled by the wrong SM count. The launcher is already filling one full wave by design.
- **Still open, and now the leading candidate:** the kernel moves ~230 GB/s of the card's ~1,792 GB/s. With block occupancy already near maximal, the remaining loss is either **bandwidth** or the **vec kernel's per-thread efficiency at head_dim 256** (255 registers per thread is a heavy footprint for a non-tensor-core path). Distinguishing those needs one decode profile at ctx 262,144 on the control binary.
- **Unchanged:** KV is on CUDA0 for exactly the 10 attention layers and `flash_attn` is enabled, so host/PCIe KV reads and non-FA paths remain eliminated; `n_embd_k_gqa = 512` over `n_head_kv = 2` gives head_dim 256; the attention penalty is 1,435 us host vs 1,375 us device (+4%), independent of expert placement.
