"""G32g (after the -np 2 runs g761-g763 and the owner-facing review): the layer-major pass takes a sequence whose KV cells are ONE CONTIGUOUS BLOCK that does not start at cell 0 (a second slot of a unified cache, -np > 1).

Before: lm_identity_ok demanded cell == position from cell 0, nothing else in the cache, and find_slot continuing the layout -- at -np 2 the second sequence (and every sequence while the other one holds cells) failed it,
so the pass was taken once in 160 soak requests.
Now: (1) llama_kv_cache::lm_block(seq, p0, n_new) returns c0, the cell of position 0 (or the start of the first run of n_new empty cells for a fresh sequence), when the sequence's cells are exactly c0 + position, one
sequence per cell, contiguous, and the n_new cells behind them are empty; -1 otherwise (the ordinary path then takes the batch, nothing changed). (2) While the pass applies a chunk, find_slot is told where to put it
(llama_kv_cache::lm_force: the cells [c0 + p0 + t0, + n) or failure), so the layout cannot drift from what the plan checked. (3) The flash-attention K and V views of the pass's graph start at cell c0 (view_offs moved by
c0 rows), so the implicit causal mask (key index == position) is exact; the K/V writes of the ubatch go to the true cells as before.

Edits: src/llama-kv-cache.{h,cpp}, src/llama-context.h (plan.c0), src/llama-graph.{h,cpp} (llm_graph_lm.kv_cell0 + the view shift), and llama-lm-prefill.cpp / .h (patched here in stage-c, then copied)."""
