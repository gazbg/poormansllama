 - The hybrid decode works in the UNMODIFIED server as soon as its environment and the expert placement are set: decode graphs of width <= `GGML_MOE_HYBRID_MAX_WIDTH` (= 4) are built with the hybrid ops when the context has no layer-streaming object attached (`llama_moe_hybrid_build_ffn`). TG is 3.5x stock with a hand-set 57-slot cache. Nothing sizes the cache to the keep-free rule in the server yet.
 - The prefill with the hybrid environment is 2.3x faster than the same placement without it (419 against 175 tok/s) -- the engine registers the host expert pages (page-locked), which speeds the host-to-device expert copies of the stock prefill; to be confirmed and kept.
 - Prompt-cache reuse is the stock server's and works for this hybrid / recurrent model (cache_n 4,089 of 4,093; the last tokens are re-decoded for logits).
 - With the hybrid on, a cache-hit continuation diverges from the cold run after ~45 tokens (`g203`, `g206`, `g208`; identical under `CUDA_LAUNCH_BLOCKING=1`). The cause is numerics, not state: the cold run computes the last prompt tokens through the 512-row batch (GPU experts), the cache-hit run re-decodes them through the hybrid ops (host leg for missed experts), and the greedy text flips at a near-tie. The test criterion therefore has to be "equal up to a near-tie flip" (logprob margin of the flipped token), never byte equality (AGENTS.md: answer stability, not token identity).
 - A trap met: `LLAMA_KV_LAZY=0` still ENABLES the lazy KV (the variable is only tested for presence): the first server probe crashed with an illegal memory access because nothing committed the KV rows. The server needs the on-demand commit before lazy KV can be used (task S2).

## Design

 1. **A hybrid-decode preset in the server** (`--hybrid-moe`): sets the engine environment defaults (only if the user did not), keeps the MoE expert banks on the host (the `-cmoe` override), turns the fit step's expert placement off, and after the model is loaded and warmed up sizes the expert cache to the keep-free target (the existing `--fit-target`, default margin of the server) with the runner's auto-sizing rule; the cache is re-sized when an idle slot's context has grown (the KV commit eats the margin).
 2. **Lazy KV with on-demand commit** inside `llama_kv_cache` (rows committed as cells are written, also for state restore), so that the cache gets the VRAM the unused part of a 262k window would take.
 3. **Layer-major prefill inside `llama_decode`** for large prompt batches of one sequence (the server's `-b` batches): the controller must take (a) a start position n_past > 0 (the prefix is in the KV / recurrent state), (b) any sequence id, (c) a per-request chunk layout and tail width (the sets are cheap: 41 ms for the three width classes), (d) a mode switch per call (stock graph path with the hybrid ops for ordinary batches, layer-major sweep for large ones) WITHOUT freeing its slot / slab buffers, (e) the output rows in the context's normal output buffer (so `llama_get_logits_ith` works). Resident cost: 2 layer slots (996 MiB) + one segment of slab + the 2048-row scheduler buffer (1.8 GB) taken from the expert cache; the cost is measured, not assumed.
 4. **Tests**: a multi-turn harness (`tools/server-probe.py` + scenarios + a checker) covering prefix reuse, branching, checkpoints, the host prompt cache, long growth, concurrency, and an equivalence check against the stock path with the near-tie rule.

## Contract G31 (written 2026-10-14 BEFORE the first server source edit; none of these may move after a result)

**Definitions.** STOCK = the unmodified `llama-server` of this tree (side copy `bin/s0`) with the owner's flags. OPT = the same binary family with `--hybrid-moe` (and, from S3, `--lm-prefill`). A "turn" = one request. TG = the response's `timings.predicted_per_second`; PP = `timings.prompt_per_second` over the tokens actually processed. All sessions: mains power, one session at a time under the GPU mutex, no host work during a timing session.

 - **SRV-1 default-off identity.** Without the new flags the server is the stock server: same load log, same memory, greedy outputs identical to `bin/s0` for the smoke scenario, TG / PP within 3%.
 - **SRV-2 decode.** With `--hybrid-moe` (auto-sized cache): TG >= 3.0x STOCK in the same session at 4,093 and 24,000 tokens of context, and >= 2.0x at 100,000 (the cache shrinks as KV grows). Sampling parameters of a typical client (temp 0.6, top-p 0.95, top-k 20) are covered, not only greedy.
 - **SRV-3 memory.** Over every multi-turn session (growth to >= 100,000 tokens of context): the in-process free VRAM minimum (sampled externally by `nvidia-smi` every 100 ms) stays >= 16,000 MiB when the keep-free target is 16,000, and no CUDA OOM / allocation failure occurs; the cache re-sizing never runs while a request is in flight.
 - **SRV-4 prompt cache and checkpoints.** In an agentic multi-turn scenario (system prompt + tools + growing history, tool-result messages of 500-20,000 tokens) every turn after the first processes at most (new tokens + 64) prompt tokens when its prompt extends the previous prompt + response; a branch that diverges inside the history resumes from a checkpoint at or before the divergence (`cache_n` >= the checkpoint position) and never reprocesses from token 0 unless no checkpoint <= divergence exists; the host prompt cache (`--cache-ram`) restores an older conversation after another one used the slot. These are the STOCK server's rules (same flags); OPT must keep them: per turn `prompt_n` OPT <= `prompt_n` STOCK + 8.
 - **SRV-5 equivalence.** For every scenario request: the OPT greedy continuation of a cache-hit turn equals the OPT continuation of the same prompt processed from scratch (`cache_prompt:false`) up to a near-tie flip: at the first differing token the two top-2 logprobs of the reference differ by < 0.25 nats (recorded), and up to that token the texts are identical. Hard failures: a differing token with a larger margin, an empty / garbled response, an HTTP error.
 - **SRV-6 stability.** A soak of >= 150 requests (mixed lengths, cache hits and misses, concurrent requests with `-np 2` in a separate session, cancelled requests) ends without a crash, a hang, a leak (free VRAM at the end within 64 MiB of the start after the same sizing; host RSS growth < 1 GiB) or a telemetry / assertion failure in the server log.
 - **SRV-7 prefill (S3).** With `--lm-prefill`: the PP of a prompt suffix of >= 20,000 tokens is >= 2.5x STOCK's in the same session; the continuation after it is equivalent (SRV-5) to the stock-path prefill of the same prompt; a turn whose new suffix is < the threshold takes the stock path and costs the same as OPT without `--lm-prefill`; the prefix reuse (SRV-4) is unchanged; TG after a layer-major prefill is >= 0.95x TG after a stock-path prefill (the mode switch costs nothing in decode).
 - **SRV-8 no regression of the runner.** The runner (`llama-layer-streaming`) keeps its recorded behaviour: ids identical for the G30-1 cells, host tests 78/78 + 5/5.

**Claims allowed.** Exactly what is measured, on this machine, for this model, with the flags used. NOT claimed: other models / architectures, multi-GPU, `-np > 2`, vision, MTP in the server (stretch S5, separate contract if built), a physical 8 GiB card.

**Escalation.** A crash or a mismatch is root-caused (reproduced, instrumented, bisected) before a criterion is discussed. The owner is not asked; unresolved facts are resolved by a reversible probe, the vendored sources or primary documentation.

## Test scenarios (the harness)

 - T1 prefix reuse: request, repeat, extension (cache_n ~ prompt_n of the previous turn).
 - T2 agentic chat: `/v1/chat/completions`, a system prompt with tool definitions (~3k tokens), then N turns, each appending the assistant message and a user/tool message of 0.5-20k tokens.
 - T3 branch: from a conversation of N turns, a request that keeps the first k turns and changes turn k+1 (rollback to a checkpoint).
 - T4 two conversations alternating on one slot (host prompt cache / similarity slot reuse), then return to the first.
 - T5 long growth to >= 100k tokens with periodic quality probes.
 - T6 concurrency: `-np 2`, overlapping requests, one cancelled mid-stream.
 - T7 sampling parameters of a typical client.
 - T8 equivalence: cache-hit versus `cache_prompt:false` with `n_probs` margins (SRV-5).

### Decisions (recorded before the run)

 - **D1 mechanism: per-launch pieces, not persistent graph sets.** The runner's controller prebuilds persistent graph sets for ONE fixed layout (chunk positions, KV slots, recurrent cell, attention window baked/snapshotted, memory cleared after the build). A server batch has any start position, any size, any tail width, a recurrent cell that may be fresh or continuing. Building each piece (embed, one layer of one chunk, head) when it is launched, with the ordinary `model.build_graph` + `res->set_inputs` from that chunk's OWN memory context, makes all of that correct by construction and removes the set menu, the snapshot restore, the slab-slice claims and the stale-address hazard of persistent graphs (G28). Cost: one graph build + allocation + input upload per launch (measured, reported as `build / alloc / inputs` in the pass log). Alternative considered and rejected: generalising `layer_major_pp` (900 lines of fixed-layout assumptions, snapshot/patch machinery).
 - **D2 the pass runs on its own `ggml_backend_sched`** (created per pass, swapped in by `lm_run`, freed at the end): the context's persistent decode graphs keep the compute buffer they were planned on (a buffer that GROWS frees the old one under every graph that already ran: G28), and the pass's compute buffer is returned to the expert cache.
 - **D3 resources exist only while a pass runs**: slot window (2 x 498 MiB), activation slab (one segment), pass scheduler. With the hybrid engine `llama_lm_vram_hook` makes room first (the expert cache shrinks as for the prefill window) and the cache grows back afterwards.
 - **D4 recurrent state**: after the first chunk is applied, the recurrent cell is normalised to what the in-graph "zero cell `rs_z`, gather from `src0`" would produce (memset the donor cell, copy the source cell into the head cell), so every chunk of the pass runs with the identity gather that the shared memory state shows once all chunks are applied.
 - **D5 flash attention** uses the implicit causal mask (`ggml_flash_attn_ext_set_causal`), which addresses keys by cell: a batch is taken only when `llama_kv_cache::lm_identity_ok` holds (the sequence's cells are exactly cells 0..p0-1 with position = cell, nothing else in the cache, `find_slot` continues the layout). Everything else takes the ordinary path.
 - **D6 stock TG**: the flag is independent of `--hybrid-moe`. Layers whose routed experts are host-resident stream; layers with experts on the device (`-ncmoe N`, the fit step) compute in place (`set_pp_cpu_layers` "native leg"); the decode after the prefill is whatever the context does.
 - **D7 logits**: only the last token's (the server's prompt batches ask for nothing else); a batch that asks for more takes the ordinary path.

## G42 -- np 1: one layer-major pass per request (checkpoints taken INSIDE the pass) and idle-time preparation of the next pass (written 2026-10-18 BEFORE the first G42 code edit and run)

**Authority.** Owner message 2026-10-18, a session /goal (a Stop-hook condition, NOT the autonomous-mode phrase of AGENTS.md: nothing is staged / committed / pushed, no decision is "accepted" as owner approval): "I do not expect to support parallel requests so NP equals 1 is fully okay. Their major must be using 2 slots [layer slots]. And also you can have an optimization on top of that because we limit to NP1. You can at the end of each request prepare for the prompt prefill for the next one, so prepare the 2 swaps before even the next request arrives. And then obviously on top of that you have to find how to make this work with the existing checkpoint ... so that you don't need to compute the whole context every time. So try to implement this, and if you can't implement it, then try to figure out why." Same rules as G31/G32.

**Reading of the goal (stated, so it can be checked).** (1) `-np 1` only; the pass keeps its 2 layer slots (`--lm-prefill-slots 2`, the default). (2) "Prepare the 2 swaps before the request arrives" = at the end of a request, in the idle time, make room (the expert cache shrinks), allocate the slot window and the slab and start the copy of the banks of the first two streamed layers; the next request's pass then starts at once. (3) "Work with the existing checkpoints so the whole context is not recomputed": the pass must keep the server's context checkpoints (the recurrent-state snapshots of positions in the prompt) AND resume from them; today it does by cutting every request into several batches (before the last user message, 516 tokens before the end, 4 tokens before the end) and every cut batch that is not a pass copies all 40 expert banks again. The goal asks for the checkpoints to cost nothing extra: they are taken INSIDE the one pass. I read "figure out why" as: if a part is infeasible, the evidence of why replaces it.

### Baseline (measured 2026-10-18 with `LLAMA_SRV_PHASE_LOG=1`, `tools/server_phase_timeline.py`, build `bin/s47` = s46 + the phase log; fixture agentic-A, 11 turns, np 1, `--hybrid-moe --lm-prefill`)

 - Default mode (`k5001-prof-def-agentic`): mean request wall 4.98 s = 4.49 s of prompt batches + 0.41 s after the last prompt batch (answer tokens). A typical request is: a 30-50 token batch before the last user message (0.5-0.6 s, ordinary path, it copies the used banks), the main batch (the pass, 1.0-5.9 s, or ordinary 0.97-1.2 s when < 1,024 tokens), the 512-token checkpoint batch (1.2-1.3 s, ordinary path: all 40 banks again), the 4-token batch (0.03 s, or 0.37-0.40 s when the expert-cache regrow lands in it). Per request the pass has a fixed ~0.23 s to start (`resources: acquire` 228 ms, almost all of it the cache shrink: `room for 1750 MiB made`) and the regrow is ~0.4 s.
 - Canonical mode (`k5002-prof-canon-agentic`): mean 4.83 s = 4.04 + 0.75; the batch after the aligned checkpoint (224-1,916 tokens) is an ordinary-path batch of 1.05-2.43 s.
 - Reading: of a ~5 s request ~2.2 s are second and third bank streams that only exist because the server cuts the batch to take a checkpoint, ~0.3 s the pass's set-up. The prediction (an estimate, not a result) is a request of ~3.2 s with the checkpoints fused into the pass and ~0.3 s less with the set-up prepared in the idle time.
 - Break-even of the idle preparation: the arm costs a cache regrow (~0.4 s, at the first small decode) when the next request does not use the pass, and saves ~0.3 s when it does; it pays only if more than ~57% of the next requests use the pass. Hence a policy (`auto`).

### Decisions (recorded before the run)

 - **D1 scope: `-np 1` only, opt-in.** New flags `--lm-prefill-fuse`, `--lm-prefill-fuse-min N`, `--lm-prefill-prearm {off,always,auto}`; they refuse `-np > 1`, speculative decoding and `--lm-prefill`-less runs at start-up (loud). Flags off = s47/s46 exactly.
 - **D2 fusion mechanism: snapshot, do not cut.** The server builds ONE batch for the rest of the prompt (up to `-b`), no cut at the places where it would have taken a checkpoint, and tells the library the token counts where a checkpoint is wanted. The pass cuts a chunk boundary there (in addition to the multiples of the chunk size) and, after the chunk that ends at the boundary has gone through a recurrent layer, copies that layer's two recurrent-state rows (conv `r`, SSM `s`) to the host. After the pass the library writes each snapshot as the SAME blob `llama_state_seq_get_data_ext(PARTIAL_ONLY)` would have written at that position (the real serializer, with the rows and the cell position substituted), and the server stores it as the checkpoint. Layer-major order makes this exact: the state of layer L after chunk k is exactly the state a batch ending there would have left. Cost: 63 MiB of host copy per snapshot (~6 ms).
 - **D3 which positions: the legacy rule, simulated.** The server replays its own cut/checkpoint rules while it fills the batch (user-message start, `4 + n_ubatch` and `4` before the end, minimum spacing, canonical chunk boundary) against the checkpoint list as it would evolve, so the same checkpoints exist as without the flag (default mode) and the same one (canonical mode).
 - **D4 fallbacks are explicit.** Before a fused batch is built the server asks the library to ARM the pass for it (make room, allocate, check the KV layout and the recurrent position); refused = the legacy cuts (nothing changes). A pass that is declined after that (fault injection, a device error) leaves the ordinary path to process the batch with no snapshots: no checkpoint is created for that batch (never a wrong one), and the log says so.
 - **D5 threshold.** `--lm-prefill-fuse-min` (tokens left in the prompt, default 700, set by the sweep below before the acceptance runs and changed only as a recorded decision): a fused request is one pass (floor ~1.3 s) against 2-4 ordinary-path batches (0.5-1.3 s each).
 - **D6 idle preparation = the library's ARM state.** `llama_lm_prefill_arm` is the same call the server makes for a known batch and for the idle time: room via the existing hybrid hook (the cache shrinks, the room for the pass's compute buffer is kept free), slot window + slab + pass scheduler allocated, the banks of the first `n_slots` streamed layers copied (`load_layer`). The pass adopts the armed resources when the slab is big enough, otherwise releases and acquires normally. Any decode of <= 16 tokens, or a big batch the pass cannot take, disarms (release; the cache regrows at the first small decode exactly as after a pass).
 - **D7 idle policy.** `always`: arm at the end of every request. `auto`: arm when at least 2 of the last 4 requests used the pass. TTL for an idle arm: none (an armed server holds the same memory as an unarmed one with a smaller cache; no wake-up thread added).
 - **D8 blob equality.** The checkpoint made from a snapshot is compared with the legacy one by a hash line (`LLAMA_LM_LOG=1`): in canonical mode the legacy checkpoint at the aligned position is made after a PASS over the same chunks, so the two must be byte-identical.
