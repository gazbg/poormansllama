# Dense decode ring on Windows (RTX 5090 Laptop, 24 GiB): does streaming layers through a slot ring beat the plain CPU split?

**Asked (owner, 2026-10-21).** For decode of the dense Qwen3.8-27B-UD-Q6_K_XL with the maximum context reserved: KV cache first, a ring of 2 slots (and the MTP head), the rest of the VRAM as constant resident layers (the full-attention layers preferred), the other layers streamed through the ring while the CPU computes its share; a formula or online tracking that decides which layer goes into the slot next so the copy is hidden behind CPU compute; conservative or optimistic estimates. Owner's remarks: more than 2 slots should not help (decode has no idle gap to fill a buffer); test with the maximum context in the server command but a ~10k-token prompt and ~50 generated tokens.

**Status.** Experiment record, not an acceptance. Agent's own decisions listed below; nothing here is owner approval. Nothing staged, committed or pushed.

## Test shape and instruments

- Machine: Ryzen 9 9955HX (16C/32T, DDR5-5600 dual channel, `-t 16`), RTX 5090 Laptop 24 GiB on PCIe Gen4 x8 (14.3 GB/s measured, 347 MiB layer = 25.4 ms), mains power. Windows 11 / WDDM.
- Model `C:\Models\ALL\other\qwen-3.8\Qwen3.8-27B-UD-Q6_K_XL.gguf`: 64 layers, 347-357 MiB each, 16 full-attention layers (3, 7, ..., 63), q8_0 KV (8,704 MiB at 262,144), host layers placed with `--lm-prefill-host-layers`, KV and recurrent state of every layer on the device.
- Harness `tools/dense/win-arm.py` (+ `win-batch.py`, `win-plan.py`): server started with the arm's flags, a 400-char warm-up, a cold 10k-token prompt (29,000 chars, 9,667 tokens), then 2 cached decodes of 50 tokens (`cache_n` 9,663, so decode starts at depth ~9.7k). VRAM from a 0.5 s `nvidia-smi` poller. Nsight Systems capture (`--nsys`) of one decode, analysed by `tools/dense/nsys-ring.py` (SQLite times are nanoseconds).
- All GPU runs went through `tools/with-gpu-lock.ps1` with `-AllowBusy` (the busy probe lists only `explorer.exe` and `dwm.exe`: the desktop compositor, 0 MiB, ~1% utilisation, no other project) and `-AllowUnprovenanced` (the Python harness names no binary to attest). **Nothing here is certified; timings carry run-to-run drift: the no-ring baseline itself moved 3.34 -> 3.65 tok/s inside one session (9%).** Only interleaved (A-B-B-A) comparisons are claimed.

## What was found

1. **The first ring on Windows was SLOWER than no ring (2.49 against 3.35-3.5 tok/s, 8 streamed layers).** Nsight (`n4-s8`): the copy engine ran at 14.3 GB/s but was only 50% busy, the host spent 232 ms per token in `cudaStreamSynchronize`, and exactly one small host-to-device copy per layer copy (160 in 20 tokens) was issued while a 347 MiB layer copy ran and waited a median **22.4 ms** behind it (3.59 s of the 8.1 s capture). Cause: one copy engine executes copies in order; the activation hop CPU layer -> GPU split queues behind the bulk copy (the repo's G23 finding for the prefill, here for decode). Counters showed 0 recoveries and 0 not-ready waits: the prefetch itself was on time. A WDDM flush after queueing (event query) gave only 4%; `--load-mode none` changed nothing.
2. **Fix: paced copy from a worker thread** (`llama-dense-stream.cpp`): the layer copy goes in pieces of 1 MiB with at most 2 in flight, issued by a worker; the compute thread blocks in `on_wait` until the worker has recorded the ready event (never waits on a stale event). Hop latency drops to ~130 us. Result at 64k ctx: **3.64 tok/s** (S=8), against 2.49 unpaced. 4 MiB pieces 3.23; 512 KiB and 256 KiB pieces are slower (the worker cannot issue fast enough: 2.97 / 1.95); window 3 and poll interval 0/20/40 us change nothing.
3. **Ceiling.** Same ring with the slot copies skipped (`LLAMA_DS_NOCOPY=1`, output garbage, timing only): **4.43 tok/s (221 ms)**. So the layer order is fine and the real DMA costs ~49 ms per token (~6 ms per streamed layer). What does NOT explain it (each measured): compute thread count (12-16), thread pinning to one logical CPU per core (worse), `--prio 2`, raw DRAM bandwidth (8-16 threads read 49.8 GB/s alone and 48-49 GB/s while a 12-13 GB/s copy loop runs; `tools/dense/dram-bw.cu`, `dram-share.sh`). About 23 ms of it is the hop wait behind 1 MiB pieces (228 hops per token); the rest is unexplained.
4. **Streamed count (64k, even-32 host set, paced; tok/s):** S=0 3.34 / 3.65 (before / after), S=4 3.76, S=8 3.63 / 3.68, S=12 2.53, S=16 1.98. Beyond ~8 the paced copy is the limit: ~11 GB/s from the worker (32 ms per layer) fits S=12 -> 395 ms and S=16 -> 504 ms. Each extra streamed layer saves ~8 ms of CPU but costs ~3-6 ms of interference, so the useful range is S=4-8 and the curve is flat there.
5. **More than 2 slots do not help (the owner's expectation holds).** S=8 with 4 slots 3.67 against 3.63-3.68 with 2; S=12 with 3 slots 2.56 against 2.53. With S<=8 the ring is idle ~25 ms after each 25 ms copy; the slots are not the constraint.
6. **Attention layers: no preference found.** Host set = odd layers (holds all 16 attention layers): no ring 3.56, ring S=8 spread over the host list 3.68 (vs even set 3.34-3.65 / 3.63-3.68). Streaming ONLY the attention layers (S=8, layers 3, 7, ..., 31) is worse, 2.99, because they are bunched at the start of the model: the copies cannot hide behind the CPU layers between them. A layer's cost does not depend on its type (352 vs 364 MB); what matters is spreading the streamed layers evenly. Placement of resident layers is cost-neutral for decode; for VRAM the full-attention layers' KV (544 MiB each at 262k) is on the device either way.
7. **Hops are not the problem:** stock contiguous placement with host KV (`-ngl 33 -fit off`, no device KV for the host layers, no hops) decodes 3.11 tok/s, slower than the interleaved placement with device KV (3.35-3.65).
8. **Maximum context (the real configuration), `-c 262144`, q8_0 KV, even-32 host set, 10k prompt, 50 tokens, paced ring:**

The fixed VRAM at 262k is ~10.5 GiB (KV 8,704 + head, state, buffers), which still leaves ~33 resident layers for decode (32 used here); the layer-major prefill pass needs ~1.1-2.7 GB on top and declines when the card is this full.
9. **MTP + ring (host layers 0-35, 28 resident, `--spec-type draft-mtp --spec-draft-p-min 0.6 --spec-draft-n-max 3`, `-c 262144`, 64 tokens):** no ring 8.19 / 8.28 tok/s (draft accepted 82-89%), ring S=4 8.67, ring S=8 8.64: **+5%**. ### Hop kernel (built 2026-10-21 after the owner asked for 'hop-aware copy pacing')

The first design, a flag the worker consults before queueing a piece, cannot work: a hop waits behind the pieces queued BEFORE it, and pieces queued after it wait behind the hop, so gating the worker changes nothing for that hop. What does help is that the hop never enters the copy-engine queue. Small host-to-device buffer copies (<= 256 KiB, the activation hops, `ggml_backend_cuda_buffer_set_tensor`) are now optionally done as: memcpy into a pinned mapped staging buffer, a copy kernel on the per-thread stream reading it with uncached loads, then the same stream sync as before (`ggml-cuda.cu`, `ggml_cuda_hop_kernel_copy`; `LLAMA_CUDA_HOP_KERNEL=1` or `ggml_backend_cuda_set_hop_kernel`; off by default for every other path). The dense ring switches it on with the paced copy (`LLAMA_DS_HOP_KERNEL=0` opts out).

Measured at `-c 262144`, even-32 host set, 10k prompt, 50 tokens (batch 15; tok/s): no ring 3.569 / 3.446; ring S=4 copy-engine hops 3.848 / 3.845; **ring S=4 hop kernel 3.973 / 3.974 (+3.3%, repeated)**; ring S=8 hop kernel 3.796; ring S=4 window 1 3.905 (+1.5%, within noise of window 2); window 1 + hop kernel 3.893 (no extra); hop kernel with no ring 3.604 (nothing to gain without the bulk copy). **All 10 arms generated the identical 50 tokens (sha1 prefix dc748d33d7), ring on or off, hop kernel on or off.** Total over no ring: about +13%.

### Owner's lookahead formula (2026-10-21, `n17-*`, `n18-*`)

**The rule as given.** The first two ring layers (0, 1) are loaded before decode starts. When a ring layer ends its slot is free; look forward over the layers, count only the layers the CPU computes (a layer already in the ring is on the device, a layer that is not a host layer is resident: neither counts), and after L of them the next host layer is the one the freed slot is loaded with (example: after layer 0 the layers 2, 4, 5 are CPU, 3 is resident, 1 is in the ring: layer 6 is loaded). Tried with L = 3, then L = 2, as asked. The rule picks WHICH layers are streamed (the plan), so it is a plan generator: `tools/dense/win-plan.py --pick lookahead|spaced --lookahead L` and the server spec `--lm-decode-stream lookahead:L` / `spaced:L` (needs `--lm-prefill-host-layers`; the log line `lm-decode-stream: spaced 3 -> ring layers ...` shows the result; the C++ ring equals the Python one, checked for spaced:3). The ring protocol itself is unchanged (the copy of ring layer k+2 is queued the moment ring layer k ends).

**Two readings, both built.** `lookahead:L`: the count starts at each ring layer that ends, as the example reads literally. Layers 0 and 1 end one after the other, so their windows (2, 4, 5) overlap and the ring comes out dense: 14 of 32 host layers at L = 3, 16 at L = 2. `spaced:L`: the count starts at the previous ring layer, so consecutive ring layers have exactly L CPU layers between them (0, 1, 6, 12, 17, 22, 28, 33 at L = 3; the example's "load the sixth" holds).

**Setup.** Max context 262144 (q8_0 KV), 10k-token prompt cached, 50 tokens, 2 decodes per arm, paced ring + hop kernel (defaults), `-t 16`, mains. Host set `natt:42` = the 32 non-attention layers of 0..41 (attention layers 3, 7, ..., 39 and layers 42..63 resident = 32 resident, as in the even-32 set). Raw: `build/dense/win/n17-*`, `n18-*` (git-ignored), batches `batch17.txt`, `batch18.txt`. Same GPU lock flags as above, nothing certified. All 21 arms generated the identical 50 tokens (sha1 prefix dc748d33d7), ring on or off.

**Reading.** (1) The formula works as a plan generator, but L = 3 and L = 2 do not pay on this machine. The paced layer copy takes ~32 ms (11 GB/s, 1 MiB pieces, 2 in flight) and a CPU layer ~8 ms, so 3 CPU layers give ~24 ms of lead: 74% of the waits find the copy unfinished (595 of 800) and the compute thread waits 3.5 ms per wait for the worker. L = 4 is borderline (166 of 800 late, flat to +4%); from L = 5 on no copy is late (0 / 21 of 480) and the token is as fast as the old spread S=4 plan. L = 2 and the dense `lookahead` variant stream 12 to 16 layers per token: the single copy engine cannot deliver 4 to 5 GiB per token, the token becomes copy-bound (this reproduces the S=12 / S=16 arms of the sweep above: 395 and 504 ms). (2) The best the formula reached (L = 5 or 6, S = 6, +7..11%) is within noise of the spread S=4 plan (+10..11%); S = 4 to 6 is a flat top. Nothing in these runs shows the formula beating an even spread. (3) Its adjacent start (0 and 1 both loaded before decode, and again at the end of every token for the next one) costs nothing visible once L >= 5 (0 not-ready waits); at L = 3 the late copies are among the waits of each token. (4) Reading the numbers: the useful L is about `ceil(copy_ms / cpu_layer_ms) + 1`, i.e. 5 here; a faster copy path (unpaced is 25.4 ms, 3 to 4 layers) would move it down to 3 or 4, but unpaced copies starve the activation hops (the finding above), so L = 3 is not reachable without a better hop path. Limits: one session per batch, 2 decodes per arm, baseline drift between the two no-ring arms of one batch 1.5..2%, only one repeat of most arms; differences of 2 to 3% inside the flat top are not claimed.

## Goal G-DYN (owner, 2026-10-21, /goal): dynamic ring + resident count

**Goal text.** Make the layer ring load dynamic: use statistics from the previous token (p95 of CPU execution time and GPU execution time) to roughly estimate which exact next layer to load in the ring, instead of a fixed spread. And the VRAM-resident layers are spread evenly by default, with a parameter for the count wanted in VRAM.

**Status.** Accepted by the agent (see 'G-DYN result' below); the owner redirected the goal away from benefit proofs (D15). Nothing here is owner approval; nothing staged, committed or pushed.

**Design (agent's decisions, recorded before the first run).**
- D7 `--lm-resident-layers N`: N layers stay on the device, spread evenly and end-aligned: layer ((i+1)*n_layer)/N - 1 for i = 0..N-1 (N=8 -> 7,15,...,63; N=2 -> 31,63; N=16 -> the 16 attention layers). The host list is the complement and is what `--lm-prefill-host-layers` would have been; an explicit `--lm-prefill-host-layers` wins over it. n_layer comes from the GGUF header (block_count - nextn_predict_layers) because the placement is decided before the model loads. Reversible, off when absent.
- D8 `--lm-decode-stream dynamic[:P]` (P = percentile, default 95): every host layer is a candidate ring layer. The ring layers are chosen by a planner (pure function, `include/llama-dense-plan.h`) from measured statistics of the previous passes: copy time of a layer (worker thread, DMA only, p-P over a window of passes), CPU cost per host layer (time between the end of one ring layer and the start of the next, minus the resident layers inside, divided by the CPU layers inside; taken at the (100-P) end because a fast CPU is the case that leaves the copy too little lead), GPU time of a ring layer (CUDA timing events, p-P). The planner walks the token timeline and, whenever a ring layer ends (its slot is free), picks as the next ring layer the first host layer whose predicted start is at least `copy_p95 * (1 + margin)` after the copy could finish (the copy engine is one: copies are serial). That is the owner's rule with the layer count L replaced by measured time (L = ceil(copy / CPU layer) at margin 0.10 gives the two optima measured above: 5 at 8 ms per CPU layer, 6 at 7 ms). The first n_slots ring layers are always the first n_slots host layers, so the copies queued at the end of a pass stay valid whatever plan the next pass uses. A ring layer must save time: it is used only if CPU-layer cost > GPU-layer cost + the copy interference (`LLAMA_DS_OVERHEAD_MS`, default 2 ms; measured 3-5 ms). The plan changes only between passes, with hysteresis (the new plan must predict >= 1% less time, or the current one must be predicted late), and a late-copy feedback widens the margin (+0.10, up to 0.6) and decays it again after a clean window. A changed plan rebuilds the decode graph once (the ring layers are bound at graph build); an unchanged plan keeps the graph reuse. Tuning knobs by environment only: `LLAMA_DS_MARGIN`, `LLAMA_DS_OVERHEAD_MS`, `LLAMA_DS_WINDOW_TOKENS` (16), `LLAMA_DS_REPLAN` (2 passes). The static list (`--lm-decode-stream 0-1,9,...`) and `spaced:L` keep working as they are.

**Owner summary.**
1. *What was asked.* Make the layer ring dynamic: use statistics of the previous tokens (p95 of the CPU and GPU execution time) to estimate which exact next layer to load into the ring instead of a fixed spread; and spread the VRAM-resident layers evenly by default with a parameter for how many you want.
2. *How it works.* The decode of the dense model is slow because most layers are computed by the CPU. The ring lets the GPU compute some of those layers: while the CPU works through a few layers, a copy engine brings the weights of the next ring layer into one of two VRAM slots. The copy takes about 33 ms and a CPU layer about 8 to 9 ms, so a ring layer must come several CPU layers after the previous one. Before, you chose that spacing by hand. Now the server measures, per decode step, how long a layer copy takes (p95), how long the CPU takes per layer (fast end) and how long a ring layer takes on the GPU, walks the timeline of the next step and picks the first layer that starts late enough for its copy to be done. It changes the plan only between steps, only if the new plan is predicted 3% faster (or copies were really late), and not twice within 8 steps. `--lm-resident-layers N` puts N layers in VRAM, evenly spread, the last one always included, and starts this ring over the rest.
3. *Glossary.* Resident layer: a decoder layer whose weights live in VRAM. Host layer: its weights stay in RAM and the CPU computes it. Ring layer: a host layer that is computed on the GPU from a slot. Slot: a VRAM buffer that holds one layer's weights. Copy engine: the GPU unit that copies RAM to VRAM (one, so copies are serial). p95 / p5: the value 95% / 5% of the samples stay below. Pass: one decode step through all layers. MTP: the model's built-in draft head that proposes several tokens per step. Layer-major prefill: processing the prompt layer by layer instead of token by token.
4. *Pros and cons.* Pros: no spacing to tune (measured: it reached the static plans' speed on res:8 and with MTP, `n26`, `n27`, `c33`, `c34`); one flag for placement plus ring (`--lm-resident-layers N`, measured, `c33`); same tokens as the static ring (measured); the plan logic is host-tested (3 of 3 tests, simulation of 300 passes). Use `--lm-resident-layers N --lm-prefill` for a card of a given size; keep the explicit `spaced:L` list if you want the exact static plan. Keep experimenting only if the CPU or the card changes a lot: re-measure whether the controller finds the new flat top.

**Design (agent's decision D16, reversible, opt-in).** `--lm-evict-layers N` (with `--lm-resident-layers`): N of the resident layers (evenly spread over them, never the last layer) are loaded in HOST memory (they join the `-ot` host list, so the pass already treats them as host layers: streamed from pinned RAM into its slot window) and the dense stream gives each a DEDICATED slot (`llama_dense_stream::dedicated`, a buffer of its own that is never recycled): in a decode step the layer is computed from its slot like a resident layer, with no marker and no copy. `suspend()` (called by the pass) frees the dedicated slots with the ring's, `begin_pass()` resumes at the first decode step (`resume()` allocates, binds and fills them again, ~30 ms per layer, then the decode graph is built again because the addresses changed). ## G-TILE (owner, 2026-10-22): head-tiled f16 conversion of a quantized K/V cache in the CUDA TILE / MMA flash attention

**Why.** With a quantized K/V cache the TILE and MMA kernels (every prefill batch, the pass included) read K and V as f16, so `ggml_cuda_flash_attn_ext_get_alloc_size` reserves, and `launch_fattn` fills, an f16 copy of the whole K and V of the layer behind the node's output: 4 KiB per context token for the dense Qwen3.8-27B (4 KV heads x 256 x 2 B x K and V), ~1 GiB at 262,144 tokens, in EVERY context that has a flash-attention node (the target and the MTP draft, each ~500 MiB at 128k). It is part of the compute buffer (`sched_reserve`), so it is resident the whole run, and it is the item that keeps an 8 GB card out of reach at long context.

**Design (agent's decision D17, reversible, opt-in).** Tile over **KV heads**: they are independent attention problems of `gqa_ratio` query heads each, so no softmax merging is needed (a tile over KV length would need it). `LLAMA_FATTN_HEAD_TILE=1` (server flag `--fattn-head-tile`) makes `ggml_cuda_flash_attn_ext` run the TILE or MMA kernel once per KV head on strided views of Q, K and V (the mask is shared), converting only that head's K and V to f16; the reservation is the scratch of ONE head (1/n_head_kv: 4x smaller for the dense model, 2x for the MoE) plus a compact output. The kernels index their output by the head count of the launch, so a head writes a compact `[token][gqa heads][DV]` buffer and one `cudaMemcpy2DAsync` per sequence places it in the real output. Applies only when: TILE or MMA kernel, K or V quantized, n_head_kv >= 2, no sinks, V not a view of K, contiguous F32 output. Everything else, and every run without the env var, takes the unchanged path. The VEC kernel (decode with a q8_0/q8_0 or q4_0/q4_0 cache, 1-2 queries) reads the quantized cache directly and never had the scratch.

## Cost model (fitted, for the planner)

`T(S) = T0 + (N - S) * c + S * (g + o)` for `S * d_p <= T`, else `T = S * d_p`, with N = host layers (32), `T0 + N*c` = 275-290 ms measured at S=0, c = CPU layer ~8 ms (hops included), g = GPU layer ~0.5 ms, **o = DMA interference 3-6 ms per streamed layer (measured, not predicted from bandwidth)**, d_p = paced copy 32 ms per layer (11 GB/s; the raw copy is 25.4 ms). Fit check (the constants were fitted on these arms, so this is a consistency check, not a prediction): S=4 -> 266 (measured 266 / 258-257), S=8 -> 272 (272-276), S=12 -> 395 (copy-bound, measured 395), S=16 -> 504 (measured 504). With o = 0 the model gives the NOCOPY ceiling 221 ms.

**Answer to the scheduling question.** The copy is never what is waited for when S <= 8: each slot's copy (25-33 ms) finishes ~75 ms before the layer is needed (0-90 "not ready" waits in 800), so neither a conservative nor an optimistic estimate of "when will the copy be done" changes the outcome. The online decision "which layer goes into the slot next" has nothing to gain here: the order is fixed by the layer sequence, the best static plan is flat over S=4-8, and the remaining loss (interference) is not a scheduling quantity. A dynamic S could at most move between 266 and 276 ms. NOT built: online tracking. (The owner then asked for copy pacing that reacts to the hops; that turned into the hop kernel above.)

## Decisions (agent's own)

- D1 Paced copy is the default of the ring on Windows (`LLAMA_DS_PIECE_KIB` default 1024, `LLAMA_DS_WINDOW` 2, `LLAMA_DS_POLL_US` 20); other platforms keep the unpaced copy (measured only on the GTX 1070 box before). `LLAMA_DS_PIECE_KIB=0` restores the old behaviour. Reversible; the ring itself stays opt-in (`--lm-decode-stream`).
- D5 Hop kernel on with the paced ring (default on Windows), because it is bit-identical on 10 of 10 arms and +3.3% twice; the shared CUDA path is untouched unless the ring (or the env var) asks for it. Reversible: `LLAMA_DS_HOP_KERNEL=0`.
- D2 A WDDM flush (event query) after each queued ring copy stays on (`LLAMA_DS_FLUSH=0` disables): small gain (4%), no downside seen.
- D3 No dynamic online scheduler (see above). No lazy KV commit: the owner asked for the maximum to be reserved; lazy commit would free ~8 GiB at 10k tokens (~23 more resident layers) but needs a policy for growth (the MoE server has one) and was not tried.
- D6 The owner's lookahead formula is built as a plan generator (`--lm-decode-stream lookahead:L|spaced:L`, `win-plan.py --pick lookahead|spaced`), both readings, opt-in; the ring protocol and every default are unchanged. Recorded result: L = 3 and L = 2 lose or tie (section above), L >= 5 ties the spread plan. Reversible; no default changed. The ring layers stay a static plan: an online choice per token was not built (the plan repeats every token).
- D4 Diagnostics kept: `LLAMA_DS_NOCOPY` (timing only), the periodic `dense-stream: ... not ready ... host stalled` line under `LLAMA_LM_LOG=1`.
- D17 G-TILE (2026-10-22): the f16 scratch of a quantized K/V cache in the CUDA TILE / MMA flash attention is converted one KV head at a time, opt-in (`--fattn-head-tile`, `LLAMA_FATTN_HEAD_TILE=1`, `ggml_backend_cuda_set_fattn_head_tile`). Options: tile over KV length (needs softmax merging), tile over KV heads (exact per head, scratch / n_head_kv), dequantize inside the kernel (a new kernel). Chosen: KV heads, the smallest change that reuses the shipped kernels unchanged. ALiBi, sinks, f16/f16 and a V that is a view of K are excluded. A setter instead of the environment for the server flag (see the result). Reversible: off by default, the untiled path is untouched.

## Claims and limits

- Measured on this machine only, Q6_K_XL only, `-np 1`, 10k-token depth, 50-64 generated tokens, 2 decodes per arm, greedy. Gains of +9% to +12% (no MTP) and +5% (MTP) are against a baseline with 4-9% session drift; the max-context pair is interleaved (no ring, ring, ring, no ring), the MTP pair is not repeated for the ring.
- Not tested: quality/equivalence of ring output against the plain split (the slots are filled from the same bytes; the bit-identity test of DQ-5(a) was run only on the Linux build, not rerun here), deeper contexts (CPU attention is not involved; GPU attention grows with depth), the layer-major prefill together with the ring on this card (the pass declines when full), `-np > 1`.
- Open: the unexplained ~25 ms of the ~49 ms DMA interference; a copy path that does not use the single H2D engine for the CPU->GPU hops (zero-copy kernel reads of the hop tensors) would remove the 23 ms hop wait.
