## What was built (all opt-in; without the flags the server is the stock server)

`--hybrid-moe` (G31): hybrid decode (expert banks on the host, VRAM expert cache sized to `--fit-target`, cache hit on the GPU / miss on the host), lazy KV commit with cache shrink, unified KV for
`-np > 1`, prefill window (ubatch 2048 only while a decode has a batch of >= 1,024 tokens; not with a fixed `--hybrid-moe-slots`).
`--lm-prefill` (G32): a prompt batch of `--lm-prefill-min` tokens or more is processed LAYER-MAJOR: for each layer the expert bank is copied from the host once into a 2-slot VRAM window (an async
feed worker copies the next bank while the current layer computes), every chunk of the batch (2,048 tokens) goes through that layer in ascending order, the activations are handed from layer to
layer through a slab (segments of 16,384 tokens), then the head runs for the last token. Resources (slot window, slab, pass scheduler) exist only while a pass runs.

| flag | default | meaning |
|---|---|---|
| `--lm-prefill` | off | enable the pass (CUDA, Qwen3.5/3.6 MoE; refuses LOUDLY at start-up when unsupported) |
| `--lm-prefill-min N` | 1024 | smallest prompt batch taken (sweep `g630`) |
| `--lm-prefill-ubatch N` | 2048 | tokens per chunk; 512 = the stock chunk shape (output equal to the ordinary path at that shape, 14-22% slower prefill) |
| `--lm-prefill-segment N` | 16384 | tokens per activation-slab segment (multiple of the ubatch) |
| `--lm-prefill-slots N` | 2 | layer slots in the VRAM window |
| `--lm-prefill-bf16` | off | bf16 activations (half the slab; NOT validated against f32) |
| `--lm-prefill-batch N` | 16384 | logical batch (`-b`) when `-b` is not given |
| `--lm-prefill-ckpt-chunk N` | 0 (= stock rule) | size of the separately processed tail that makes the context checkpoint; < 32 runs on the CPU (see the trade-off below) |
| `--hybrid-moe-frozen` | off | (round 3) deterministic hybrid decode: a fixed expert cache of `--hybrid-moe-slots` slots (default 16 here) and no promotions, so identical requests give identical output; decode 0.55-0.58x of the dynamic cache |

Chunk layout (round 3): the pass cuts its chunks at multiples of the chunk size in ABSOLUTE position, so a pass that resumes behind a cached prefix (cache hit, rollback to a checkpoint) starts with the short chunk that reaches the next multiple and cuts the rest where a fresh pass cuts them; a pass that starts at a multiple of the chunk size (every fresh prompt) is unchanged bit for bit (`k2001`). Segments hold as many whole chunks as fit in `--lm-prefill-segment` rows.

Environment (round 2): the pass's flash attention takes the ordinary path's kernel variant by default (`LLAMA_LM_FA_EXACT`, default on, and `FAFIX_CAUSAL_GQA`, which the server sets to 1 when it is not set, before the model is loaded);
`LLAMA_LM_FA_EXACT=0 FAFIX_CAUSAL_GQA=0` restores the previous behaviour bit for bit (`k1281` against the previous build's `k941`: 16 of 16 prompts token-identical, maximum logprob difference 0.000000).

With several slots (`-np > 1`, unified KV, which `--hybrid-moe` selects) `--lm-prefill` also changes WHERE the server puts things, only while the flag is on (review round 1, below): sequences are kept as contiguous blocks with gaps,
idle slots are cleared before a prompt is restored from the host cache, and a big prompt chunk is processed alone in its batch. Without the flag none of this exists.

### Round 2

**3. The deviation of the pass from the ordinary path has a cause, and it is removed (g32p, g32r).** Round 1 could only say that the pass is "not bit-identical to the ordinary path even at equal chunk shape" and that the expected cause was a
different flash-attention kernel variant. Round 2 isolated it. The pass's attention is the mask-free causal-window op on the live key range, which ggml-cuda dispatches to a kernel variant WITHOUT grouped-query packing; the ordinary path runs the masked op on a
view padded to a multiple of 256 keys, WITH packing. The reduction orders differ, so near ties move. Two switches make the pass take the ordinary path's variant: the pass's key range is the 256-padded one (`llama-graph.cpp`, `LLAMA_LM_FA_EXACT`) and `FAFIX_CAUSAL_GQA=1`
(`ggml-cuda/fattn.cu`; the server sets it before the model is loaded because ggml-cuda reads it once). Effect, measured at equal chunk shape: first token, 20 prompts in the realistic checkpoint flow, stock `-ub 512` against the pass with 512-token chunks: median 0.0000, maximum 0.0002 nats (before, 16 prompts without checkpoints: p90 0.19 and one flipped prompt, `g856`); hybrid decode with the expert cache
frozen, window against pass at chunk 512 / 2,048: maximum 0.0012 / 0.066 (before: p90 0.19 / 0.78 and a flipped prompt, `k1041`, `k1051`). The pass also got faster at long context (+2.7% / +11% / +21% at 24k / 50k / 100k) because the packed kernel reads each KV head once for its 8 query heads. This is the default now; `LLAMA_LM_FA_EXACT=0 FAFIX_CAUSAL_GQA=0` is the opt-out (bit-identical to the previous build, `k1281`).

**4. The 80 sanitizer errors were a real redundant call, now removed, and the report confirms it (g32q).** The 80 = 40 x `cudaHostRegister` + 40 x `cudaGetLastError`, error 712 "already mapped", from `llama_lm_prefill_enable` -> `register_all_pkg_sources` -> `ggml_backend_cuda_register_host_range`: the hybrid engine had pinned the spans already and the code carried on by design. Instead of arguing that they are harmless, the call is skipped:
`ggml_backend_cuda_register_host_range` asks `cudaPointerGetAttributes` whether the first and last byte of the range are page-locked host memory already and then returns false with the same message, so no caller changes. Independent check: compute-sanitizer memcheck (clean stop, `--print-limit 500`) on the final binary ends with **`ERROR SUMMARY: 0 errors`** in all four sessions: a pass that spans three activation-slab segments (`--lm-prefill-segment 4096`, a 9,000-token batch = 5 chunks, after a 2,484-token pass; `k1201`), a two-slot session (`--cache-ram 0`, distinct slots) with passes at positions 0, 0, 3,000, 2,996, 5,500 and 5,496 of two conversations, i.e. blocks that do not start at cell 0 (`k1202`), the same two on the previous build `s35` (`k1101`, `k1102`), and the window-only baseline (`--hybrid-moe` without `--lm-prefill`, same prompts, 0 passes, `k1103`). **10. An engine experiment that did not work: a host kernel that computes like the CUDA kernels (G33, reverted).** The cause of the noise is that cache-resident experts run on the GPU (CUDA `mmvq`: the activation quantized to q8_1, one fp16-rounded scale per 32 values, `q = roundf(x/d)`) and the others on the host (ggml-cpu: q8_K, one scale per 256 values): the two legs agree to ~1.5% of the output RMS, not bit for bit, and which expert runs where follows the cache state. I wrote a host quantizer and AVX2 Q4_K / Q6_K dot products that follow the CUDA formulas (`ggml-cpu/q81x.c`; host test 60,018 checks without a failure, the lean team in this mode bit-equal to a single-threaded run of the same kernels for 1-8 threads and 1-8 experts) behind `LLAMA_MOE_HYBRID_Q81=1`. Against the real CUDA kernels (up, gate, SwiGLU, down on the GPU, 20 requests, 1 and 3 tokens, Q4_K and Q6_K down banks): the old host path is 1.5% of the output RMS away on average (maximum 10-13%), the new one 5e-6 to 3e-5 (about 500-3,000x closer; 13% of the elements bit-equal; the rest differ in the last bit of the float summation order, which every now and then flips one quantization level of the next matmul). Effect on the noise (17 prompts, dynamic cache, `k1501`/`k1502` against `k1401`/`k1402`): same-request-twice median first-token distance 0.0158 -> 0.0186 (window) and 0.0159 -> 0.0155 (LM); pairs above the rule FF 5/51 -> 3/51 and 2/51 -> 1/51, HF 11/102 -> 8/102 and 4/102 -> 14/102. At a FIXED residency (frozen cache, `k1511`-`k1514`) switching only the host numerics, a change of the size the new kernels remove, moves the first token by a median 0.0185 nats (p90 0.078) and 2 of 16 continuations above 0.25: the same floor. So the activation re-quantization in every matmul turns any difference of arithmetic that is not bit-identical into the same noise floor, and only bit-exact, residency-invariant arithmetic (a custom fused GPU expert kernel, a host kernel that replicates its summation order, a canonical association of the final sum over the experts) would remove it: a redesign of the G31 engine, not done. The code is reverted from the tree and archived (`stage-c/g33*`); the proposed follow-up session for it was withdrawn.

**21. Retraction, and the canonical mode (G41, G41b).** A cache hit differs from a fresh run because the prompt is cut into batches differently: the cached prefix was computed inside an earlier request whose batches ended 516 and 4 tokens before its end (the context checkpoints), the tokens that decode produced were computed one at a time, and the resumed pass starts wherever the checkpoint was. The pass already cuts its chunks at absolute multiples of the chunk size (G35). `--lm-prefill-canonical` puts the other seams there too. (1) Context checkpoints exist only at multiples of `--lm-prefill-ubatch` (2,048): the batch that ends a prompt is cut at the last multiple below N, the checkpoint is taken when the next batch starts there; no 4 + ubatch tail, no 4-token tail, no user-message checkpoints. (2) A continuation never keeps the state that decode left behind: it resumes from the newest checkpoint that precedes the common prefix of the old and the new prompt, or from 0, and prefills everything after it. (3) At `-np > 1` every prompt batch gets a batch of its own (G41b: the size of a batch decides which path computes it, and a hit must take the path a fresh run takes). Then the tokens after a checkpoint are prefilled in the same chunks as in a fresh run, the part that is shorter than `--lm-prefill-min` takes the same ordinary path with the same batch width, and the KV below the checkpoint comes from complete aligned chunks of the earlier request. Code: `common/common.h`, `common/arg.cpp`, `tools/server/server-context.cpp` only; no CUDA or engine change; opt-in; needs `--lm-prefill`, context checkpoints and `-b` a multiple of the chunk (it refuses to start otherwise). The apply scripts are `stage-c/g41_*.py.txt`, `g41b_*.py.txt`.

**26. Where an np 1 turn spent its time (measured first, `LLAMA_SRV_PHASE_LOG=1`, `tools/server_phase_timeline.py`, `k5001` / `k5002`, s47).** Mean request 4.98 s (default) / 4.83 s (canonical). The server cuts a prompt at the places where it takes a context checkpoint (before the last user message, 516 and 4 tokens before the end), and every cut batch that is not a pass streams all 40 expert banks again: a 45-token batch 0.58 s, a 512-token checkpoint batch 1.22-1.31 s, the 4-token batch 0.03 s (0.37-0.40 s when the cache regrow lands in it). The pass itself pays ~0.23 s to start (`resources: acquire`, almost all of it the cache shrink: the cache is re-uploaded, 252 ms for 2.1 GiB) and the regrow after it is 391 ms (3.7 GiB). So about 2.2 s of a 5 s request were second and third bank streams, 0.25 s the pass's set-up.

**27. What was built.** (a) `--lm-prefill-fuse`: the rest of the prompt goes in ONE batch. The server replays its own cut and checkpoint rules while it fills the batch, against a simulated checkpoint list, and asks the library (`llama_lm_prefill_snap_request`) for the recurrent state at the token counts where a checkpoint would have been taken. The pass makes a chunk boundary at each of them, copies the two recurrent rows (`r`, `s`) of every recurrent layer to the host when the chunk that ends there has gone through the layer (63 MiB, ~25 ms per snapshot), and writes each snapshot with the REAL serializer (`llama_memory_recurrent::state_write` through a substitute writer, cell position overridden), so the blob is byte-identical to what `llama_state_seq_get_data_ext(PARTIAL_ONLY)` writes at that position; the server stores it as the checkpoint. Layer-major order is what makes this exact: layer L after chunk k holds exactly the state a batch that ended there would have left. (b) `llama_lm_prefill_arm`: room (the hybrid hook shrinks the cache), slot window, slab, pass scheduler, and the copy of the banks of the first two streamed layers; the pass adopts them. The server arms for a known batch before it builds a fused batch (refused = the legacy cuts, nothing changes) and, with `--lm-prefill-prearm`, when the slots go idle after a request (`always`, or `auto` = when 3 of the last 4 requests used the pass). (c) A decode of <= 16 tokens, or a big batch the pass cannot take, gives the prepared resources back (the cache regrows at the first small decode, as after a pass).

## The equivalence analysis (LM-3)

Three facts frame it. (1) The pass is bit-deterministic (first-token top-10 |dlogprob| 0.0000 across repetitions and servers, for WINDOW, LM, STOCK and every variant) and, with the expert cache frozen, repeatable at the text level (WINDOW against WINDOW and LM

## Owner summary

**1. Original goal.** After the G31 report the owner doubted my decision not to build the layer-major prefill and asked: compare it with the current prefill and the stock one, build it behind a parameter, and make it usable with the standard (stock)
token generation so that the pieces combine freely. A standing goal asks for an integration that is tested thoroughly with multi-turn requests, reuses the prompt cache and checkpoints, and has no mistakes. The idea: a long prompt is slow because every chunk of it
drags the whole 16.9 GiB of expert weights across the PCIe link; process the weights layer by layer instead, once per prompt. Seven reviews of the work asked whether "no mistakes" was shown. The defects they pointed at were real and are fixed (a redundant driver call, a pass that did not take the ordinary path's attention kernel, a fixed expert-cache size not respected after a pass, chunk layouts that differed between a hit and a fresh run, a segment rule that cost memory, and the np 2 cascade of memory-guard declines, root-caused from a log line: an open prefill window held 844 MiB while the pass asked for memory). One point stays open: the hybrid engine's own history-dependent arithmetic. It was measured, attacked with an engine experiment that did not work, and given a deterministic mode instead; in the shipping dynamic mode the hit-versus-fresh checks still miss in some fixture orders, as they do for the stock server (round 4 point 16). The sixth review noted that the np 2 fix was shown on one workload; it was not general (two more mechanisms of memory-guard declines, found with the G37 log line), is now fixed by G39 and G40 and measured on six more workloads against two earlier builds (round 5 point 19), and the failing hit-versus-fresh checks were measured against the stock server's own batch-shape floor (point 17). The seventh review asked why known failures were left in place; my claim that a bit-equal hit is impossible with a prefix cache was untested and wrong, and the opt-in `--lm-prefill-canonical` mode makes the five checks pass in all 12 sessions (60 of 60, 49 bit-identical, point 22) at a measured cost (point 23).

**2. How it works.** The model has 40 layers; most of its size is the routed-expert weights, which live in host RAM. The window path processes the prompt in chunks of 2,048 tokens and, for every
chunk, copies all experts to the GPU (1.17 s per chunk). The layer-major path inverts the loops: take layer 1's experts to the GPU once, push ALL chunks of the batch through layer 1, then layer 2, and
so on, copying the next layer's experts in the background while the current layer computes. The copy is paid once per batch (up to 16,384 tokens) instead of once per chunk. Only the loop order changes, the arithmetic of each piece is the same kernels,
the attention takes the same kernel variant as the ordinary path, and the chunks sit at the same absolute positions as a fresh run's, so at the same chunk size the results equal the ordinary path's to within a few thousandths of a nat. The pass is taken only when the sequence's keys sit in one contiguous block of the cache; with several slots the server
keeps them that way (gaps between sequences, tokens continuing behind their own sequence, idle slots cleared before a restore) and gives a big prompt chunk a batch of its own; otherwise the ordinary path runs.

**3. Glossary.** PP / prefill: processing the prompt before the first answer token (tokens per second, t/s). TG: token generation, the decode phase. Expert bank: the weights of all routed experts
of one layer. Hybrid decode (`--hybrid-moe`): experts stay in host RAM, the GPU keeps a cache of the popular ones, the host computes the rest. Window: G31's prefill mode that raises the
physical batch from 512 to 2,048 while a big prompt is processed. Pass: one layer-major prefill run over a batch. Chunk: tokens processed together inside a pass (default 2,048) or by the ordinary path (the ubatch, default 512). Segment: up to 16,384 rows, the unit of the
activation slab. Slot (VRAM): space for one layer's expert bank (2 are used so one copies while one computes). Slot (server): one conversation's place; `-np 2` = two. Unified KV: all slots share one KV cache (cells are shared). Cell: one token's place in the KV cache.
Checkpoint: a saved model state a few hundred tokens before the end of a prompt so a later request can resume from it instead of reprocessing. Prompt cache: the server's memory of earlier prompts (host RAM). STOCK: the unmodified server.
Near tie: two candidate tokens whose scores differ by < 0.25 nats, where float rounding can flip the greedy choice. nat: the unit of a log-probability difference (0.25 nats = a factor 1.28 in probability). Shape effect: an ordinary path changes its output when only its chunk size changes (stock `-ub 512` against `-ub 2048`).
Equal shape: pass and ordinary path using the same chunk size. Frozen cache / `--hybrid-moe-frozen`: the expert cache does not change while decoding, so the decode is deterministic. Hit / fresh: a request that reuses cached tokens against one that processes the whole prompt. Same-request noise: two runs of the identical request in one session. Residency: which experts are in the GPU cache. Knife-edge prompt: one whose first token flips between two answers under any change of shape (`eq-13`). MiB / GiB: mebibytes / gibibytes.

**4. Pros and cons.** Pros (all measured unless marked): prefill 1.39-1.41x (4k), 2.30x (24k), 2.34-2.37x (50k), 2.25x (100k) the window and 8.4-9.1x STOCK at 24k-50k (`k2170`-`k2173` and `k2870`-`k2873`, `g614`); with the stock decode 9.6x STOCK at 24k-50k (`k1311`); an agentic turn with 6-20k new tokens 1.6-2.0x faster than the window (`k2155`);
decode, prompt cache, checkpoints and memory margin unchanged (TG 33.4 -> 34.3 t/s, prompt_n identical to STOCK in every request of both suites, 36 of 36 in each, free VRAM minimum >= 16,031 MiB); the first generated token is deterministic; 160-request soaks clean at np 1 and np 2;
fault paths recover; two slots: every sequential turn taken; works with stock decode; the runner is unchanged (texts byte-identical); compute-sanitizer memcheck: 0 errors; on the contract's own four prompts the first token is within 0.07 nats of STOCK and 0.053 of the window and the continuations match the window with no flip above 0.25; at an equal chunk size the pass reproduces the stock and the hybrid paths (first token to 0.0002-0.066 nats, 63 of 64 continuations within the 0.25-nat rule), and `--lm-prefill-ubatch 512` gives that at 14-22% lower pass rate (still 1.8x the window); the opt-out of the attention change reproduces the previous build bit for bit; **a deterministic mode (`--hybrid-moe-frozen`) in which identical requests give identical output and every hit-versus-fresh expectation of the original fixtures is met (np 1 and np 2), with 0 of 102 replicated hit-versus-fresh pairs above the rule (price: decode 0.55-0.58x)**.

the opt-in canonical mode removes them (60 of 60 checks, round 6 point 22) at the price of re-prefilling up to one chunk per follow-up**; a host kernel that computes like the CUDA kernels was built and measured (500-3,000x closer to the GPU) and did not lower that noise, so only a bit-exact residency-invariant engine would (not done); at the DEFAULT chunk the output differs from the stock server's as much as the stock server's differs from itself under a batch-size change, so a 0.25-nat rule holds for the first token and for continuations against the window but not for 64-token continuations against STOCK (2 of the contract's 4 prompts; the window misses the same two); one equal-shape continuation (of 64) crosses the 0.25-nat rule (0.357, `eq-09`); under concurrent clients 4-17 big batches per run are declined because they hold tokens of two sequences and are served by the window; **5. Recommendation.** Adopt `--lm-prefill` as the prefill path for long prompts and agentic sessions, single or two slots: `--hybrid-moe --lm-prefill -fitt 16000` for the full speed, `--lm-prefill -ngl 99 -ncmoe N -fit off -kvu` (with `-np 2`) with stock decode.

## Owner summary -- G42 (np 1: checkpoints inside the pass, and the pass prepared in the idle time; the agent's own acceptance under the standing /goal, NOT owner approval)

**1. Goal.** "np 1 is fine; use the two layer slots; at the end of each request prepare the next prompt prefill (the 2 swaps) before the next request arrives; make it work with the existing checkpoints so the whole context is not recomputed; implement it or explain why not." It matters because a coding agent sends many small-to-medium turns; each used to spend ~2 s of a ~5 s request on extra expert-bank streams that exist only because the server cuts the prompt to take checkpoints, plus ~0.25 s to set the pass up.

**2. How it works.** The server used to cut every prompt into 3-4 batches to take a checkpoint (a saved copy of the recurrent state) between them; every cut batch re-copied all 40 expert layers from host memory. Now the whole prompt tail goes through ONE layer-by-layer pass, and when a layer has processed the chunk that ends at a checkpoint position, its recurrent state is copied aside; afterwards the checkpoints are written from those copies with the normal serializer, so they are the same bytes as before. When the server goes idle it makes room (shrinks the GPU expert cache), allocates the two-layer window, and copies the first two layers' experts, so the next pass starts at once.

**3. Glossary.** Pass / layer-major prefill: processing a long prompt layer by layer so each layer's experts are copied once. Checkpoint: saved recurrent state of the model at a prompt position, so a follow-up request resumes there. Slots / window: the two GPU buffers that hold the experts of the layer being computed and the next one. Expert cache: GPU copy of the most-used experts for token generation; it is shrunk to make room for the pass and regrown after. Arm: prepare the pass (room, window, slab, first banks). Slab: GPU buffer for activations between layers. FUSE: the one-batch prompt. prearm: arming in the idle time. BASE: the same server without the new flags. Canonical mode: checkpoints only at chunk-size multiples so a cache hit equals a fresh run bit for bit. Think time: the pause between turns (a user or a tool).

**4. Pros and cons.** Measured (build `s53`, 3 s think time, A B B A, two sessions per arm, mean request wall): agentic transcript 4.841 s -> 3.656 s with `--lm-prefill-fuse` (0.755x), 3.456 s (0.714x) with `--lm-prefill-prearm always`, 3.520 s with `auto`; canonical mode 4.721 s -> 3.715 s (0.787x); a transcript of small turns (326-887 new tokens) 0.902x, `auto` costs nothing there (1.003x of fuse), `always` +4.9%. Same prompt tokens processed as before in every request, same checkpoint positions, canonical checkpoints byte-identical to the legacy ones (8 of 8), stock-decode and frozen-cache hits bit-identical to fresh runs (20 of 20 checks, 102 of 102 pairs), soaks 3 x 160 requests clean, memcheck 0 errors, host tests 78/78. Flags off = unchanged server (per-request wall 0.994-1.003x). Costs and limits: one dynamic-cache check missed the 0.25-nat rule by 0.017 (decode noise of the dynamic expert cache, not the prefill; contract GA-5 (a) NOT MET as written, measured); an unused idle preparation costs a cache regrow (+0.37-0.40 s) (`auto` limits it); a pass that is declined after the arm leaves no checkpoint for that batch (only seen with injected faults); ~0.64 s per pass request is still the expert cache's full re-upload on shrink and regrow (not built: an in-place resize); only `-np 1`, no speculative decoding or multimodal; proven on one 24 GiB card emulating the 16,000 MiB rule, not a physical 8 GiB card.

**5. Recommendation.** Adopt for single-conversation use: `--hybrid-moe --lm-prefill --lm-prefill-fuse --lm-prefill-prearm auto -np 1 -fitt 16000` (add `--lm-prefill-canonical` where a cache hit must equal a fresh run). Keep `--lm-prefill-fuse-min` at 700 (break-even ~610 tokens). Next candidate, in order of value: an in-place resize of the expert cache (removes most of the 0.64 s), then fewer extra checkpoints (a faster, shallower-rollback mode). To decide: whether the dynamic cache's residual decode noise matters for your use (it never affects stock decode or the frozen cache).
